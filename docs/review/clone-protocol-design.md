# clone プロトコル設計書(F5 `cloneWiki` / F7 `openRepository`)

**この文書はレビュー専用です。実装 PR にもマージ先ブランチにも含めません。**

対象ブランチ: `gitlab-ls-9.3.0` / 関連 issue: #14(D15)/ 前サイクルの設計書: Close 済み Draft PR #70

## 1. 背景と目的

D15 の 8 コマンドのうち 6 つ(F1〜F4 / F6 / F8)は前サイクルで設計・実装を終えた
(PR #71 #72 #73 #76 #77 #78)。残る **F5 `cloneWiki`** と **F7 `openRepository`** は、
前サイクルの Codex レビュー 7 巡を通じて **「clone 先の所有権・確定・異常終了からの回復」プロトコル**が
繰り返し指摘の中心になり、方式を 3 度変えても
**「自分が作ったものだけを消す」ことを保証できない**という同じ壁に当たったため、
ユーザー判断で独立サイクルへ切り出された(前設計 §4.1)。

本設計の目的は、**その壁を回避する方針を確定させたうえで** F5 / F7 を実装可能な形にすることである。

### 1.1 前サイクルで未解決だった指摘(本設計の入力)

| 指摘 | 内容 |
|---|---|
| 第 3 巡 R3-7 | `CloneCommand` の内部作成物を呼び出し側から識別できない |
| 第 5 巡 R5-2 | `ATOMIC_MOVE` は宛先存在時の置換可否が実装依存(Linux は空ディレクトリを置換する) |
| 第 6 巡 R6-1 | `createDirectory` はディレクトリの作成者を保証するだけで、子要素の所有者は保証しない |
| 第 7 巡 R7-1 | **名前の秘匿は所有権の根拠にならない**(ディレクトリは列挙・監視から発見できる) |
| 第 7 巡 R7-2 / R7-3 | ステージング昇格時の同名衝突、予約と永続記録の間のクラッシュ窓 |

### 1.2 本設計の中心的な決定(2026-08-15・ユーザー判断)

> **D1: 失敗しても、このプラグインのコードは一切削除しない。**

上記 5 件の指摘はすべて **「作った物を安全に消す」** ための機構に関するものである。
**消さないと決めれば、機構ごと不要になる。** 代償は「失敗時にディスク上に途中経過が残りうる」こと。

**「データ損失は発生しない」とは書かない**(第 8 巡 R8-3)。**このプラグインのコードが削除しない**
というだけであり、**JGit の `cleanup()` による削除経路が残る**(下記の受容済み制限)。
**D1 が保証するのは「このプラグイン自身が所有権の不明なものを消さないこと」であって、
無損失ではない。** 実装計画にも**無損失保証として転記してはならない。**

これは既存機能の方針
(F6 §12「作成したプロジェクトも remote も削除しない」/ F4「外部の変更を上書きするくらいなら
中間状態のまま残す」)とも一貫する。

**この決定は本設計の全体を規定する。以降の節はすべてこの前提の上に立つ。**

**ただし JGit 自身は削除する**(第 4 巡の検証で判明・実バイナリで確認)。
`CloneCommand.cleanup()` は失敗経路で次を行う:

- `directoryExistsInitially` が false → **`FileUtils.delete(directory)` で宛先ごと削除**
- true → **`deleteChildren(directory)` で中身を削除**

**したがって D1 は「このプラグインのコードが削除しない」という意味であり、
「ディスク上に必ず何かが残る」という意味ではない。**§13.2 (b) の文面はこれを踏まえる。

> **【受容済み制限・ユーザー判断 2026-08-15】JGit の `cleanup()` は、clone 実行中に
> 宛先へ書き込まれたファイルも削除する。**(第 5 巡 R5-2)

入口判定(D2)が保証するのは**判定時点で空だったこと**だけである。**clone の実行中に
ユーザーや外部プロセスが宛先へ書き込むと、fetch 失敗時の `deleteChildren(directory)` が
それを再帰的に削除する。****`CloneCommand` の cleanup は API から介入できない**ため、
**この経路は防げない**。前サイクルの A18 と同じ扱いとし、**「起きない」とは主張しない**。

**露出を減らす措置**(受容するが、窓は狭める):

- **宛先を事前作成しない。** `directoryExistsInitially` が false になり、cleanup の対象は
  **JGit 自身が作ったディレクトリ**に閉じる。**空ディレクトリをユーザーが用意して指定する運用を
  推奨しない**(§22 U1 の入力 UI は「親 + 新しいフォルダ名」を既定とする)。
- **進捗ダイアログで clone 中であることを見せ、**「**clone 中は指定した場所に書き込まないでください**」
  と明示する。
- 窓は「**見えている clone 先に、clone 中に書き込む**」場合に限られる。

**`cleanup()` は `call()` が失敗を返す経路でしか走らない。** JVM や Eclipse が
**異常終了した場合は走らない**ため、そこでは中途半端な clone がそのまま残る(§13.2 (b) / §9.4-5)。

**ただし「異常終了した場合だけ残る」とは言えない**(第 7 巡 R7-3)。**`cleanup()` は削除を
「試行する」だけで、完遂を保証しない** — ファイルロック、権限エラー、同時書き込みなどで
**削除しきれずに残物が生じうる**。したがって規範は次のとおり:

> **失敗時には `cleanup()` が走る(異常終了時は走らない)。いずれの場合も、残物の有無は
> 通知の直前に「宛先が非空か」を確認して決める(実在の有無ではない・R8-2)。** 「必ず残る」とも「必ず消える」とも書かない。

これは §13.2 (b) と C24 が要求する残存確認と同じ規範であり、**通常の失敗経路でも省略できない**。

## 2. 対象範囲

- **F5 `cloneWiki`**: 現在のリポジトリに対応する GitLab Wiki を clone し、ワークスペースへ取り込む。
- **F7 `openRepository`**: GitLab プロジェクトを指定して clone し、ワークスペースへ取り込む。

前設計 §4 の決定を引き継ぐ: VSCode の `gl.openRepository` は仮想 FS(`gitlab-remote://`)で
**clone せずに**開くが、Eclipse に相当機能が無いため **「選んで clone して取り込む」に再定義**する。
**VSCode との挙動差が生じる**(ディスク消費・初回時間)。台帳 #7 に注記する。

## 3. 対象外(意図的に実装しない)

- **仮想ファイルシステム**(`gitlab-remote://` 相当)。Eclipse に基盤が無く、本サイクルの範囲を超える。
- **このプラグインのコードによる、失敗した clone の削除・ロールバック**(D1)。
  **JGit 自身の `cleanup()` による削除は対象外にできない**(§1.2 の受容済み制限)。
  「自動削除が一切起きない」という意味ではない。
- **プロジェクト種別の推定インポート**(m2e / buildship の呼び出し)。**新規依存を作らないため**(D3)。
- **SSH での clone**(D4)。
- **submodule の取得**、**部分 clone / shallow clone**、**特定ブランチの指定**。
- **clone 済みリポジトリの更新(pull)**。

## 5. 前提条件と制約

- **同梱 JGit は 7.5.0**(`org.eclipse.jgit-7.5.0.202512021534-r.jar`)。
- **EGit UI (`org.eclipse.egit.ui`) には依存していない**(ビルドの p2 リポジトリに EGit は入っているが、
  依存として取っているのは `org.eclipse.jgit` / `org.eclipse.jgit.ssh.apache` / `org.apache.sshd.osgi` のみ)。
  **したがって EGit のクローンウィザードへの委譲は「必須依存の追加」を意味し、本設計では採らない。**
- 認証は既存 `GitAuthConfigurer` のみを使う。トークンを URL に埋めない。
- headless の devcontainer では **ワークベンチ依存の動作(取り込み)を検証できない**。手動検証に回す。

## 6. 決定事項(ユーザー判断・2026-08-15)

| ID | 決定 | 根拠 |
|---|---|---|
| **D1** | **失敗しても、このプラグインのコードはディスクの内容を削除しない**(第 4 巡で「一切自動削除しない」から限定。**JGit の `cleanup()` は削除する**) | §1.2 |
| **D2** | **clone 開始前に「宛先が存在して非空なら開始しない」だけを判定する**(第 1 巡 R1-1 で改訂) | **失敗段階を確実に区別するため。**これは所有権の判定ではなく入口の分岐であり、§1.1 の壁とは別物 |
| **D3** | **`.project` があればインポート、無ければフォルダ名で単純プロジェクトを作る** | m2e / buildship への依存を作らない |
| **D4** | **HTTPS 固定** | API に到達できているなら必ず通る。SSH は鍵・エージェント・`known_hosts` に左右され、headless で検証できない失敗モードが増える |
| **D5** | **`ProgressMonitor` アダプタ + `setTimeout`** を実装する | 前設計 §14-1 が要求し、F6(PR #77)で見送った宿題。clone はこれが最も要る場面 |

**D2 は当初「事前判定をせず JGit に任せる」だったが、第 1 巡 R1-1 で改訂した。** 判定しないままだと、
既存の非空ディレクトリを指定した場合も clone 途中の失敗も**同じ失敗経路**になり、
§13.2 が所有権を主張できない以上、復旧手順が「プラグインが何も作っていないディレクトリの削除」を
ユーザーに指示しうる。**それは D1 が回避したはずの所有権問題を手動操作へ移すだけで、
データ損失に直結する。** 入口で分岐すれば、失敗段階を確実に区別できる(§13.2)。

## 7. システム構成

```
[UI] CloneWikiHandler / OpenRepositoryHandler
        │  (SWT: 入力・確認・通知。UI スレッド)

        ▼
[背景] RepositoryCloner ──uses──▶ EclipseProgressMonitorAdapter
```

## 8. コンポーネントの責務

| コンポーネント | 責務 | 依存 | 試験 |
|---|---|---|---|
| `EclipseProgressMonitorAdapter` | JGit `ProgressMonitor` を実装し Eclipse `IProgressMonitor` へ委譲。`isCancelled()` が Eclipse 側のキャンセルを返す | なし(純ロジック) | **単体可** |
| `WikiUrlDeriver` | 末尾スラッシュを落とし、**末尾の `.git` があれば除いて** `.wiki.git` を付ける | なし | **単体可** |
| `CloneTargetLookup` | プロジェクト → 存在検証 + `http_url_to_repo`。**F5 と F7 の両方が使う** | `GitLabApiClient` | **単体可**(MockK) |
| `RepositoryCloner` | `CloneCommand` の実行。auth / monitor / timeout を設定。**削除経路を持たない** | JGit / `GitAuthConfigurer` | **単体可**(`file://` の実リポジトリから実 clone) |
| `ClonedProjectImporter` | clone 先をワークスペースへ取り込む | Eclipse Resources | **headless 不可** → 手動検証 |
| ハンドラ 2 本 | 入力・確認・通知・スレッド境界 | SWT | **headless 不可** → 手動検証 |

## 9. 処理フロー

### 9.1 `cloneWiki`(F5)

1. **[UI]** アクティブエディタのファイルを取得。無ければ通知して終了。
2. **[背景]** `GitLabProjectUrlResolver.resolveContextForFile` でプロジェクトを解決。
   解決できなければ通知して終了。
3. **[背景]** **常に API の `http_url_to_repo` から** wiki URL を導出する(第 1 巡 R1-5 で確定)。
   `CloneTargetLookup` で解決済みプロジェクトの `http_url_to_repo` を取得し、
   `WikiUrlDeriver` に渡す。**リポジトリの remote URL は「どのプロジェクトか」の解決にだけ使い、
   URL の組み立てには使わない。**
   - **D4 で clone を HTTPS 固定と決めた以上、remote が SSH か HTTPS かに関わらず
     clone に使う URL は同じ**であり、remote を分岐の材料にする理由が無い。
   - **SSH remote しか無いリポジトリでも F5 は動く。** 中止しない。
   - API が失敗した場合は §13.1 の定型文で中止する(clone は開始しない)。
4. **[UI]** clone 先を入力させる(親ディレクトリ + フォルダ名)。**キャンセルで終了、副作用ゼロ**。
4a. **[背景/UI]** **入口判定**(D2)。宛先が存在して非空なら:
   - **同一 URL のリポジトリがあり、ユーザーが取り込みに同意したら** clone を省略し、
     6 の取り込みへ飛ぶ(§13.2 (a0))。
   - そうでなければ **§13.2 (a) で中止**(削除は案内しない)。
   - **孤立した登録の解除は、ここでは一切行わない**(第 6 巡 R6-2)。**§9.4-5 でのみ提示する。**
5. **[UI→背景]** `IProgressMonitor` 付きの Job で `RepositoryCloner.clone` を実行。
6. **[背景/UI]** 成功なら `ClonedProjectImporter` で取り込み。
7. **[UI]** 結果を通知。

### 9.2 `openRepository`(F7)

1. **[UI]** プロジェクトパスを入力させる(U3 の方針を踏襲。検索ピッカーは作らない)。
2. **[背景]** `CloneTargetLookup` で存在検証し、`http_url_to_repo` を得る。
   見つからなければ通知して終了。
3. 以降は §9.1 の 4〜7 と同一。

### 9.3 clone の実行(共通)

1. `CloneCommand` に `setURI` / `setDirectory` / `setProgressMonitor(adapter)` /
   `setTimeout(TRANSPORT_TIMEOUT_SECONDS)` を設定し、`GitAuthConfigurer.applyAuth` を通す。
2. `call()` の結果は `Git` を返すので **必ず `close()` する**(ハンドルを開いたままにしない)。
3. **例外・キャンセルのいずれでも、こちらからは何も削除しない**(D1)。

### 9.4 取り込み(共通・D3)

**手順の順序について**(第 7 巡 R7-1)。**1 / 2 の「同名プロジェクトが既にある」判定より前に、
必ず 5 の判定を行う。** 5 は番号が後ろにあるが**評価順は先**である。
**1 / 2 が同名の存在だけで先に中止すると、5 の location 比較と登録解除に到達できず、
C20 の回復経路が実装順序の上で閉じる**(番号順に実装されるとそうなる)。分岐は次の順:

> **同名プロジェクトが存在する** → **5 を評価**(**閉じている** かつ **location が clone 先と一致**か)
> → **該当し、同意がある**なら登録を解除して 1 / 2 の作成へ進む
> → **該当しない、または同意が無い**なら 1 / 2 の「取り込まない」通知で終了する。

1. clone 先に **`.project` があれば**: `IWorkspace.loadProjectDescription` で読み、
   **`setLocationURI` で clone 先を指してから** `IProject.create(description)` → `open()`。
   **location の設定は必須である**(第 8 巡 R8-1)。**`loadProjectDescription` は読み込んだファイルの
   親を location として設定しない**ため、そのまま `create` すると **`${workspace}/${projectName}` に
   別のプロジェクトが作られ、clone した内容は取り込まれない**(しかも成功したように見える)。
   **2 と同じく、`create` より前に location を設定する。**
   - **例外**: clone 先がワークスペース既定location(`${workspace}/${projectName}`)そのものである場合、
     Eclipse は既定location の明示指定を拒否する。**その場合は location を設定しない**
     (`null` のまま)。**判定は「clone 先がワークスペースの既定 location と一致するか」で行う。**
   - **ワークスペース直下だが既定location と一致しない場合は、取り込みを行わない**
     (第 9 巡 R9-1)。同梱 Eclipse Resources 3.21.0 の `LocationValidator` は、
     **ワークスペースルート直下の明示的な location を `${workspace}/${projectName}` 以外すべて拒否する**。
     入力 UI は任意の親 + フォルダ名を許すため、**`.project` のプロジェクト名が `foo` なのに
     clone 先が `${workspace}/bar`** という組み合わせが成立し、この場合 `setLocationURI` しても
     `create` が失敗する。**`create` を試す前に判定して `ImportSkipReason.LOCATION_REJECTED` で
     取り込みを飛ばす**。**これは §9.4-3 の扱いなので、文面は `RepositorySource` で分ける**
     (第 10 巡 R10-1)。**(a0) から取り込んだ経路では clone を実行していない**ため、
     **`ADOPTED_EXISTING` の文面に「clone は完了した」を含めてはならない**(C31 に反する)。

     > (**`CLONED_NOW`**)「clone は完了しましたが、**ワークスペース直下のこの場所は
     > 取り込めません**(Eclipse の制約により、ワークスペース直下ではフォルダ名をプロジェクト名
     > `<.project の名前>` と同じにする必要があります)。
     > **フォルダ名を `<.project の名前>` にするか、ワークスペースの外の場所を指定してください。**
     > **clone した内容はそのまま残っています。**」

     > (**`ADOPTED_EXISTING`**)「**ワークスペース直下のこの場所は取り込めません**
     > (Eclipse の制約により、ワークスペース直下ではフォルダ名をプロジェクト名
     > `<.project の名前>` と同じにする必要があります)。
     > **フォルダ名を `<.project の名前>` にするか、ワークスペースの外の場所を指定してください。**
     > **この場所の内容は変更していません。**」

     **判定条件**: **clone 先の親がワークスペースルートであり、かつ
     clone 先のフォルダ名が `description.name` と一致しない。**
     **`.project` が無い経路(手順 2)ではプロジェクト名 = フォルダ名なので、この条件は成立しない。**
   - **入力 UI は、親ディレクトリにワークスペースルートを選ぶことを推奨しない**(この制約の存在を
     入力時に示す)。**ただし禁止はしない** — 既定location と一致する指定は有効だからである。
   **同名プロジェクトが既にワークスペースにある場合は、まず 5 を評価する**(上記の順序)。
   **5 に該当しない場合にのみ**取り込みを行わず、その旨を通知する
   (既存プロジェクトを勝手に差し替えない)。
2. **`.project` が無ければ**: フォルダ名でプロジェクトを作り、`IProjectDescription.setLocationURI`
   で clone 先を指す(1 と同じ例外規定が適用される)。
   **名前が衝突する場合も、まず 5 を評価する**(上と同じ)。
   **5 に該当しなければ取り込まない。**
3. **取り込みの失敗は clone の失敗ではない。** ただし **文面は経路によって分ける**(第 7 巡 R7-2)。
   **(a0) から既存のリポジトリを取り込んだ経路では clone を実行しておらず、
   その内容が完全かどうかは判定していない**(§13.2 (a0))。「clone は完了した」と通知してはならない。
   - **今回 `call()` が成功した経路**:
     「clone は完了しましたが、取り込めませんでした。手動でインポートしてください。」
   - **(a0) から既存のリポジトリを取り込んだ経路**:
     「指定した場所のリポジトリを取り込めませんでした。**この場所は今回 clone したものではありません。**
     手動でインポートしてください。」
   **成功時の通知も同様に分ける**(「clone しました」/「既にあったリポジトリを取り込みました」)。
   §10.3 の `CloneOutcome` は**どちらの経路かを型として保持する**。

   > **この分岐は全称である**(第 10 巡 R10-1)。**`ImportSkipReason` のどの値についても、
   > 通知は `RepositorySource` で分ける。** 個別の理由に固定文面を置いてはならない。
   > **`ImportSkipReason` を追加するときは、その文面を 2 経路分書くまでが追加である。**
   > (R10-1 は、第 9 巡で追加した `LOCATION_REJECTED` にこの規則を適用し忘れたものである。)
4. **`create()` が成功して `open()` が失敗した場合の補償**(第 1 巡 R1-3 で追加)。
   不正な nature/builder、リソース障害、ワークスペースエラーで `open()` は失敗しうる。
   放置すると**閉じた `IProject` がワークスペースに残り**、次回は 1/2 の同名衝突で拒否されるため、
   「手動でインポート」の案内でも復旧できない。したがって:
   - **`IProject.delete(deleteContent = false, force = true, monitor)` で
     ワークスペース登録だけを解除する。** `deleteContent = false` なので **clone の中身は消えない** —
     D1(ディスクの内容を消さない)と両立する。消すのは**直前にこのフローが作った登録だけ**であり、
     **所有権は明確**(§1.1 の問題とは異なる)。
   - **この補償自体が失敗した場合**は、**ディスク内容を残す操作を具体的に示す**(第 2 巡 R2-3)。
     **「削除してください」とだけ案内してはならない** — Eclipse の削除ダイアログには
     **「Delete project contents on disk」のチェックボックス**があり、
     単に Delete を案内すると**ユーザーが clone 全体を失う経路が残る**。
     文面は手順を明示する:

     > 「ワークスペースに閉じたプロジェクト `<名前>` が残っています。
     > プロジェクトを右クリック → **Delete** →
     > **「Delete project contents on disk」のチェックを外したまま** OK してください。
     > **チェックを入れると clone した内容も消えます。**」

     **ディスク上の clone には触れない。**
   - **`create()` 自体が失敗した場合は登録が作られていない**ので、補償は不要。
5. **`create()` 後・`open()` 前に Eclipse が異常終了した場合の回復**(第 2 巡 R2-4)。
   補償(4)は `open()` の失敗を**捕捉できた場合**しか働かない。プロセスが落ちれば閉じた `IProject` が
   残り、**再起動後は「このフローの所有物だ」と判定する永続情報が無い**ため、
   次回は 1/2 の同名衝突で拒否され、**取り込みが恒久的に塞がれる**。
   **永続記録は導入しない**(§12)。代わりに、**取り込み時に観測できる事実**で回復する。
   **この回復を提示できるのは、実際に §9.4 の取り込みまで到達した場合だけである**(第 6 巡 R6-2)。
   第 4 巡でこれを入口判定より前(旧 §9.1-4a)へ移したが、**宛先が別リポジトリや git でない内容だと
   登録だけ解除して直後に §13.2 (a) で中止し、clone も再取り込みもしないまま
   ワークスペース登録を失う**経路が生まれていた。**入口判定の時点では解除を提示しない。**
   移動の動機だった「回復可能性が clone の完了状態に依存する」問題は、
   **第 5 巡で (a0) から完了判定を外したことで既に消えている**(§13.2 (a0))。
   - 同名のプロジェクトが**閉じており**、かつ**その location が今回の clone 先と一致する**場合、
     **前回の中断で残った登録である可能性が高い**と判断する。
     **ただし自動では解除しない** — ユーザーが自分で作った可能性を排除できないため。
   - **明示的な同意を求める**:
     「同名のプロジェクト `<名前>` がありますが、閉じており、場所は今回の clone 先と同じです。
     前回の中断で残ったものと思われます。**登録だけ解除して取り込み直しますか?**
     **ディスク上の内容は消えません。**」
   - 同意があれば `delete(deleteContent = false)` してから 1/2 を再試行する。
     **同意が無ければ取り込まず**、§9.4-4 と同じ手順(チェックを外して Delete)を案内する。
   - **location が一致しない同名プロジェクトは、この経路に入れない。** 別物なので触らない。

### 10.1 REST

**参照実装からの意図的な逸脱(第 1 巡 R1-4)**: 参照実装は `url.replace(/\.git$/, '.wiki.git')` だが、

この入力は現在の解決経路から排除されていない。**その場合 F5 は Wiki ではなく本体リポジトリを clone し、

`http_url_to_repo` を **nullable フィールドとして `GitLabProject` に加算的に追加**する
(既存の利用箇所は影響を受けない)。**新規サービスを作るか既存を拡張するかは実装計画で確定する。**

### 10.3 主要インターフェース(案)

```kotlin
/**
 * リポジトリがどこから来たか。通知の文面を分けるために必要(第 7 巡 R7-2)。
 * ADOPTED_EXISTING の内容が完全かどうかは判定していない(§13.2 (a0))。
 */
enum class RepositorySource { CLONED_NOW, ADOPTED_EXISTING }

sealed interface CloneOutcome {
  data class Cloned(val directory: File) : CloneOutcome
  /** 取り込みまで完了。 */
  data class Imported(
    val directory: File,
    val projectName: String,
    val source: RepositorySource,
  ) : CloneOutcome
  /** 取り込めなかった。ディスク上のリポジトリ自体は有効。 */
  data class ImportSkipped(
    val directory: File,
    val reason: ImportSkipReason,
    val source: RepositorySource,
  ) : CloneOutcome
  data object Cancelled : CloneOutcome
  /** [type] は例外の型名のみ。メッセージは載せない(§13.1)。 */
  data class Failed(val type: String, val directory: File) : CloneOutcome
}

enum class ImportSkipReason { NAME_TAKEN, NO_WORKSPACE, IMPORT_FAILED, LOCATION_REJECTED }
```

**`source` が `ADOPTED_EXISTING` の結果に「clone は完了した」という語を含めてはならない**(§9.4-3)。
**`Cloned` / `Failed` / `Cancelled` は `CLONED_NOW` の経路にしか現れない**((a0) では clone しない)。

## 11. データモデル

**永続化する状態を持たない。** 前サイクルで問題になった「予約」「永続記録」は D1 により不要になった。
これは本設計の重要な性質であり、**R7-3(予約と永続記録の間のクラッシュ窓)が構造的に消える**。

## 12. トランザクション境界

**ディスク上の内容については、戻す操作自体を持たない。** 状態は次の 3 つのいずれかで、
**いずれもディスク上に観測できる**:

| 状態 | 観測 | 扱い |
|---|---|---|
| clone 先が存在しない | ディレクトリ無し | 何も起きていない |
| clone 先が空 | ディレクトリ有り・空 | 入口判定を通り、clone を開始できる |
| **同一 URL の取り込み候補** | **有効な git リポジトリで、`origin` の URL が今回の clone URL と一致する** | **完了しているかは判定しない**(§13.2 (a0))。**同意を得てから §9.4 の取り込みへ進む**。**同意が無ければ何も変えない** |
| **それ以外の非空** | ディレクトリ有り・非空(壊れた `.git` / 別リポジトリ / git でない中身) | **§13.2 (a) で中止**。**このプラグインは何も作っておらず、削除も案内しない** |

**この表は「完了したか」で状態を分けない**(第 6 巡 R6-1)。**`origin` は実 fetch の前、`HEAD` は
checkout の前に確定する**ため、**on-disk から完了を判定できる観測は存在しない**(§13.2 / 第 5 巡)。
したがって「有効なリポジトリだから完了している」と読める分類を規範として置かない。
**同一 URL の一致は同一性の判定であって完了の判定ではなく、必ず (a0) の同意へ接続する。**

**clone を開始したあとに失敗・キャンセルした場合にディスクへ何が残るかは、この表では決めない。**
`call()` が失敗を返した経路では **JGit の `cleanup()` が宛先ごと、または中身を消していることが多く**、
**異常終了した場合は残る**(§1.2)。**§13.2 (b) は通知の直前に「宛先が非空か」を確認して文面を選ぶ**(C24)。
**このプラグインのコードは、どちらの場合も削除しない**(D1)。

**ワークスペース登録は別の軸であり、こちらは戻す**(第 1 巡 R1-3)。ディスクの内容と違って
**所有権が明確**(直前にこのフローが `create` したもの)であり、放置すると次回の取り込みを
恒久的に塞ぐため:

| 状態 | 観測 | 扱い |
|---|---|---|
| 登録なし | ワークスペースに無い | 何も起きていない |
| **`create` 済み・`open` 失敗** | 閉じた `IProject` が残る | **`delete(deleteContent=false)` で登録だけ解除**(§9.4-4) |
| 解除も失敗 | 閉じた `IProject` が残る | **通知して手順を案内**(§9.4-4)。ディスクには触れない |
| **`create` 後・`open` 前に Eclipse が異常終了** | 閉じた `IProject` が残る | **§9.4-5 の回復経路**(第 2 巡 R2-4) |
| 取り込み完了 | 開いた `IProject` | 正常 |

**異常終了で残った登録を「永続記録」で追跡はしない**(第 2 巡 R2-4 への対応方針)。
所有権を永続化すると、**前サイクルで D1 が消したはずの「予約と永続記録の間のクラッシュ窓」(R7-3)が
そのまま戻ってくる**。代わりに **§9.4-5 で、取り込み時に観測できる事実から回復する**。

## 13. エラー処理

### 13.1 JGit のメッセージを素通ししない

JGit の例外メッセージは **リモート URL を含みうる**(前設計 §13)。
ユーザー向けは定型文、ログは**例外の型名のみ**とする。

> 例: 「clone できませんでした。リポジトリへアクセスできない可能性があります。」

**非空の宛先はこの経路に入らない**(第 2 巡 R2-1)。改訂後の D2 は clone 開始前に非空を検出し、
**§13.2 (a) の専用通知へ分岐する**。したがって **§13.1 の定型文に「空でない可能性」を含めない** —
含めると、実装者がこの節に従って**所有権不明の宛先を §13.2 (b) の削除候補として扱いうる**。
**入口判定は一意である。**

### 13.2 残物の通知(A9 の明示的な例外)

**失敗した段階によって文面を変える**(第 1 巡 R1-1)。D2 の入口判定があるため、この 2 つは確実に区別できる。

**(a0) 宛先が非空で、そこに「今回 clone しようとしたのと同じリポジトリの clone」がある場合**
(第 3 巡 R3-1)— **同意を得たうえで、clone を省略して §9.4 の取り込みへ進む。**
**「完了済み」とは呼ばない**(第 6 巡 R6-1)。**完了しているかは判定しない**からである。

`create()` 後・`open()` 前の異常終了から**同じ clone 先で再実行**すると、そこには前回の clone が
あるため、これが無いと (a) で終了し、**§9.4-5 の回復経路に永久に到達しない**
(別の空の場所を選んでも location が一致しないので同じく到達しない)。**恒久的な取り込み阻害が残る。**

**「完了済みか」を自動判定しない**(第 5 巡 R5-1 / R5-3)。**信頼できる on-disk の完了マーカーが
存在しないため**である。実バイナリで確認した事実:

- `fetch()` は **`RemoteConfig.update()` → `StoredConfig.save()` を実 fetch の前**に行う。
  → 中断されても「有効な repo + 一致する `origin`」は成立する(第 4 巡 R4-1)。
- `checkout()` は **`RefUpdate.link()` / `forceUpdate()` で `HEAD` を更新した後に
  `DirCacheCheckout.checkout()`** を実行する。
  → **checkout 中断でも `HEAD` は解決できてしまう**(第 5 巡 R5-1)。**`HEAD` は完了判定に使えない。**
- **空のリポジトリを正常に clone した場合は `HEAD` が解決できない**(第 5 巡 R5-3)。
  → `HEAD` を要求すると、**正常完了した空リポジトリを取り込み直せなくなる**。

**したがって判定をやめ、ユーザーの明示的な同意に置き換える。**
これは本設計が §9.4-5 で既に採っているパターン(**証明できないものは同意で解く**)と同じである。

**(a0) の条件**は次の 2 つだけにする:

1. 宛先が**有効な git リポジトリ**である。
2. **`origin` の URL が今回 clone しようとした URL と一致する。**

満たす場合、**clone を行わず、次を提示して同意を求める**:

> 「この場所には**同じリポジトリの clone が既にあります**。**これを取り込みますか?**
> (clone はやり直しません。**中身は変更しません**。)
> **前回が中断されていた場合、内容は不完全かもしれません。**
> やり直したい場合は取り込まず、**別の空の場所**を指定してください。」

- **同意があれば §9.4 の取り込みへ進む。** **何も削除せず、何も上書きしない。**
- **同意が無ければ (a) と同じ案内**(別の空の場所)で終了する。**削除は案内しない。**
- **1 か 2 を満たさない場合**(壊れた `.git`、別リポジトリ、git ですらない)は (a) へ落とす。

**この方式は空リポジトリでも中断後でも同じ経路を通る**ので、R5-1 / R5-3 の両方が閉じる。

**(a) 宛先が非空で、(a0) にも当たらない場合** — **プラグインは何も作っていない。**

> 「指定した場所は空ではないため、clone を行いませんでした。**何も変更していません。**
> **別の空の場所を指定して**やり直してください。」

**削除を一切促さない。** ここでディレクトリの削除を案内すると、**プラグインが何も作っていない
既存データをユーザーが消しうる**(第 1 巡 R1-1)。**D1 が回避したはずの所有権問題を
手動操作へ移すことになる**ため、この経路では「別の場所」だけを案内する。

**(b) clone を開始したあとに失敗・キャンセルした場合**

**JGit の `cleanup()` が走ったかどうかで、残るものが変わる**(§1.2)。**通知の前に、宛先の存在ではなく
「残存内容の有無」を確認して文面を選ぶ**(第 8 巡 R8-2):

> **判定は「宛先が非空か」で行う。「宛先が存在するか」ではない。**
> ユーザーが**既存の空ディレクトリ**を指定した場合、`deleteChildren(directory)` は
> **子要素だけを消してディレクトリ自体は残す**ため、`exists` だけを見ると
> **「途中経過が残っています」という誤った分岐**になる。
> **宛先が存在しても空なら「何も残っていない」側の文面を使う。**

> (**宛先が無い、または空の**場合)「clone は完了しませんでした。
> **指定した場所には何も残っていません。** やり直すか、別の場所を指定してください。」

> (**宛先が非空の**場合)「clone は完了しませんでした。**このプラグインは何も削除していません。**
> `<clone 先>` に途中経過が残っています。**中身を確認したうえで**削除するか、
> 別の場所でやり直してください。」

**「必ず残る」と書かない。** `call()` が失敗を返した経路では JGit 自身が消していることが多い。
**ただし「その経路では必ず消える」でもない**(第 7 巡 R7-3)— `cleanup()` は削除を試行するだけで、
ロック・権限・同時書き込みにより**残ることがある**。**異常終了した場合は `cleanup()` 自体が走らない。**
**したがって、どちらの経路でも通知の直前に「宛先が非空か」を確認して文面を選ぶ**(C24)。

- **削除を「指示」しない。「中身を確認したうえで」判断させる。**
  入口判定により、この経路の宛先は**開始時点で存在しないか空だった**ので、
  中身は今回のものである蓋然性が高い。それでも**外部プロセスが同時に書いた可能性は排除できない**ため、
  断定はしない。
- **パスを通知に含めるのは、A9 の趣旨に対する意図的な例外である。**
  A9 が守るのは「ユーザーが与えていない情報の漏洩防止」であり、
  **この clone 先はユーザー自身がその場で入力した値**であるため、返して見せることは漏洩に当たらない。
  **ログには出さない**(ログは持ち出されうるため、型名のみ)。

## 14. タイムアウト・リトライ・冪等性

- **タイムアウト**: `TransportCommand.setTimeout(30)`(§10.2)。
  **progress callback に到達しない状態(経路が無い・接続がブラックホール)は
  `isCancelled()` では抜けられないため、タイムアウトが最後の砦になる。**
- **キャンセル**: `EclipseProgressMonitorAdapter.isCancelled()` が Eclipse の `IProgressMonitor` を返す。
  **Eclipse の Job が monitor を持つだけでは JGit のブロッキング transport は止まらない**ため、
  アダプタを必ず `setProgressMonitor` で渡す(前設計 §14-1)。
- **リトライ**: **自動リトライしない。** 失敗を提示し、再実行の判断をユーザーに委ねる。
- **冪等性**: **clone 自体は非冪等**だが、**同じ場所への再実行は入口判定で分岐する**
  (第 3 巡 R3-3。改訂前の D2 の記述をここに残していた)。JGit に委ねない:
  - **同一 URL のリポジトリがある** → **同意を得てから** clone を省略して取り込みへ進む(§13.2 (a0))。
    **「完了済みだから省略する」ではない**(第 6 巡 R6-1)。**完了は判定できないので同意で解く。**
    **同意が無ければ何も変えずに終わる。**
    **結果として、同じ操作の再実行は取り込みまで含めて安定した結果になる。**
  - **それ以外の非空** → **入口判定で中止する**(§13.2 (a))。**削除は案内しない。**

## 15. 並行処理

- **clone は「正規化した clone 先パス」をキーに直列化する**(第 1 巡 R1-2 で改訂)。
  **当初は「同一 clone 先への同時実行は JGit が拒否する」としていたが、これは排他保証にならない。**
  `CloneCommand` の宛先検査は check-then-act であってロックではなく、2 つの clone が
  **宛先の作成・非空化より前に同時に検査を通過**すると、両方が同じ作業ツリーと `.git` を
  初期化・更新できてしまう。失敗するだけでなく、**破損したリポジトリ**や
  **一方が成功を通知した後に他方が書き換える**状態が生じる。D2 の事前判定も同じ理由で
  排他にはならない(判定と作成の間に窓がある)。
- **既存 `GitOperationGuard` をそのまま流用できる。** 同クラスの `withRepo(key: String)` は
  **キーが任意の文字列**(`ConcurrentHashMap` のキー)であり、`gitDir` である必要はない。
  clone の開始から完了(取り込みの前)まで保持する。**専用の guard を新設しない。**
- **キーは「ファイルシステム上の同一性」で作る**(第 2 巡 R2-2)。
  既存 guard は**文字列の完全一致しか比較しない**ため、`toAbsolutePath().normalize()` 程度では
  **symlink 経由と実体パス**、**大文字小文字を区別しない環境での表記違い**が別キーになり、
  **同じ実ディレクトリへの 2 つの clone が同時に guard を取得して**破損を再発させる。規則:
  1. **存在する最も近い祖先**を `Path.toRealPath()` で解決する
     (clone 先自身は存在しないか空なので、`toRealPath()` が使えるとは限らない)。
  2. 残りの相対セグメントを連結する。
  3. **1 と 2 を連結したキー全体を小文字化する**(第 3 巡 R3-2)。
     **祖先部分だけ元の大小文字を残してはならない。** clone 先 `.../Foo` が未作成なら
     最初の実行のキーは「実在親 + `foo`」だが、その実行が `Foo` を作成した直後
     (**まだ空なので D2 を通る**)に 2 つ目が来ると、最も近い実在祖先は `.../Foo` 自身になり、
     残りセグメントが無いためキーは `Foo` のままになる。**同じ宛先なのに 2 つの guard を取得でき、
     R1-2 の破損が再発する。**
- **小文字化は意図的に「過剰に寄せる」側の選択である。** 大文字小文字を区別するファイルシステムでは
  `Foo` と `foo` は別ディレクトリなので、このキーは**本来別物を同一視しうる**。
  その場合の結果は「同じ場所への clone が実行中」として**中止される**だけであり、
  **過剰な統合は安全側・不足した統合は破損側**なので、前者を選ぶ。
- **同一キーが取れなかった場合は「同じ場所への clone が実行中」として中止する**
  (guard は待たずに `null` を返す既存挙動)。
- **UI スレッド境界**: 入力・確認・通知・取り込みの `IProject` 操作は UI スレッド。
  clone は背景。既存 `WorkspaceProjectPicker` の形(UI で読む → coroutine → `asyncExec` で戻る)を踏襲する。
- 例外がコルーチンから漏れると**共有 plain-Job スコープが道連れで停止する**(issue #16)。
  すべての `launch` で `CancellationException` は再送出、それ以外は封じ込める。

## 16. 認証と認可

- clone は **`GitAuthConfigurer.applyAuth` のみ**を使う。HTTPS + `oauth2:<token>`。
- **トークンを URL に埋めない。ログに出さない。**
- D4 により SSH transport は使わないが、`GitAuthConfigurer` は SSH transport にも
  プラグイン所有の `SshdSessionFactory` を設定する既存挙動を持つ。**この挙動は変更しない。**

## 17. ログ・監視・監査

- ログは**例外の型名と、種別を表す短い語のみ**。URI・パス・トークンを出さない(A9)。
- 通知は §13.2 の規定に従う。

## 18. 障害時の復旧方法

**プラグイン側にディスク内容の復旧経路を持たない**ことが設計上の性質である(D1)。
**ただし「削除して再実行」を唯一の手順として案内してはならない**(第 1 巡 R1-1)。
復旧は失敗した段階によって分かれる:

| 段階 | 状態 | 案内する手順 |
|---|---|---|
| **宛先が非空で開始しなかった**((a)) | **何も変更していない** | **別の空の場所を指定して再実行。削除は案内しない** |
| **宛先に同一 URL のリポジトリがあり、取り込みに同意しなかった**((a0)) | **何も変更していない** | **別の空の場所を指定して再実行。削除は案内しない** |
| clone 途中で失敗・キャンセル(`call()` が失敗を返した) | **JGit の `cleanup()` が削除を試行する。完遂は保証されない**(ロック・権限・同時書き込みで残りうる) | **通知の前に宛先が非空かを確認する(存在の有無ではない)**(§13.2 (b) / C24)。**残っていなければ**「何も残っていません」と伝えて再実行を案内。**残っていれば**中身を確認したうえで削除するか別の場所で再実行 |
| clone 途中で **JVM / Eclipse が異常終了**した | **`cleanup()` が走らないので途中経過が残る** | 同上(非空かを確認したうえで案内)。**このプラグインのコードは削除しない** |
| `open()` 失敗 | 閉じた `IProject` が残る | 自動で登録解除を試みる(§9.4-4)。失敗したら手順を案内 |

**この表は「必ず残る」も「必ず消える」も前提にしない**(第 7 巡 R7-3)。
**残存確認(非空判定)は異常終了の場合だけの手順ではなく、`call()` が失敗を返した通常の経路でも省略できない。**
`cleanup()` の削除は API から介入できない受容済み制限であり(§1.2 / R5-2)、
**存在しない残物を案内することも、残った残物を「何も残っていません」と案内することも、
どちらもユーザーを誤らせる。**

**ワークスペース登録だけは、所有権が明確なので自動で解除する**(§12)。

## 19. 既存機能への影響

- `GitLabProject` に nullable フィールドを 1 つ追加する(§10.1)。**既存の利用箇所は影響を受けない。**
- **`EclipseProgressMonitorAdapter` は clone 専用にせず、`BranchPushService` からも使えるようにするか**は
  **未決事項 U3**(§22)。
- それ以外の既存コードは変更しない。

## 20. 移行方法・ロールバック方法

- 永続状態を持たないため、**移行は不要**。
- ロールバックは PR の revert で完結する。**ユーザーのディスクに残った clone は revert しても残る**が、
  それは通常のディレクトリであり、プラグインが管理しているものではない。
