## 3. 対象外(意図的に実装しない)

| 項目 | 理由 |
|---|---|
| スニペットの編集・削除 | VSCode 拡張にも無い(パリティ対象外) |
| 個人スニペット(`/snippets`) | VSCode はプロジェクトスニペットのみ扱う |
| 多アカウント選択(`pickAccount`) | 本プラグインは**単一アカウント設計**。VSCode の `pickAccount` は「設定済みインスタンス 1 件」に読み替える。多アカウント化は D1 の課題として分離 |
| `gitlab-remote://` 仮想ファイルシステム | Eclipse に相当機能が無く、EFS プロバイダの自前実装は独立した大基盤になる(§4 で決定を記録) |
| スニペットのページング全走査 | 初版は先頭ページのみ。`pageInfo.hasNextPage` は取得して**打ち切りを明示**する(§11) |
| **バイナリ変更を含むパッチ**(第 4 巡 R4-4・第 5 巡 R5-4 で判定を具体化) | 同梱 JGit 7.5 の `DiffCommand` / `DiffFormatter` は、バイナリ変更について **`Binary files differ` しか出力せず内容(literal/delta payload)を持たない**。そのまま F3 でスニペット化しても **F4 で post-image を再現できない**。**検出点と対象形式を次のとおり定める** —<br>**F3(生成側・POST の前に拒否)**: 差分の各エントリについて**旧 blob と新 blob を `RawText.isBinary` 等で判定**し、バイナリと判定されたものが 1 つでもあれば**作成しない**。件数のみ通知(パスは出さない)。<br>**F4(適用側)**: パースした**全 `FileHeader` の `PatchType`** を検査し、**`BINARY` を 1 つでも含むパッチは適用しない**。これにより **payload を持たない marker-only(`Binary files differ`)と `GIT binary patch` の双方を拒否**する。「バイナリハンクの有無」だけで判定すると **marker-only を素通しさせる実装が成立してしまう**ため、判定は `PatchType` で行う。<br>Git binary patch の生成対応は別サイクル |

## 4. 現在の課題と、`openRepository` に関する決定

VSCode の `gl.openRepository` は `GitLabRemoteFileSystem`(スキーム `gitlab-remote://`)によって
**クローンせずに**リモートリポジトリをワークスペースとして開く。Eclipse には相当機能が無い。

**決定(ユーザー判断・2026-08-12)**: `openRepository` は **「プロジェクトを選んでクローンし、
ワークスペースに取り込む」** に再定義する。`cloneWiki` と実装基盤を共有できるため。

**この決定の帰結(レビュー時に検証してほしい点)**:

- VSCode との**挙動差**が生じる。VSCode は書き込み可能な仮想 FS、本設計はローカルクローン。
- ディスク消費と初回時間が VSCode 版と大きく異なる。
- 台帳 #7 の D15 該当行には「Eclipse ではクローン方式」と注記が必要。

## 9. 処理フロー

### 9.1 `createSnippet`(F1)

1. **[UI]** アクティブエディタを取得。無ければ「開いているファイルがありません」で終了。
2. **[UI]** 可視性を選択(`Private` 既定先頭 / `Public`)。キャンセルで終了。
3. **[UI]** ソースを選択(`Snippet from file` / `Snippet from selection`)。キャンセルで終了。
4. **[UI]** 選択に応じて本文と**ファイル名**(パスの最終要素)を読み取る。
   選択範囲の場合、VSCode は**選択終端の次の行頭まで**を含める(行単位に丸める)。同挙動とする。
5. **[背景]** プロジェクト文脈を解決 → 数値 ID を解決(§10・U1)。
6. **[背景]** `POST /projects/{id}/snippets` に `{title, file_name, visibility, content}` を送る。
7. **[UI]** 応答の `web_url` を既存 `BrowserLauncher` で開く。

### 9.2 `insertSnippet`(F2)

1. **[UI]** アクティブエディタが無ければ終了。
2. **[背景]** GraphQL でプロジェクトスニペット一覧を取得。0 件なら通知して終了。
3. **[UI]** スニペットを選択 → blob が複数なら blob も選択。
4. **[背景]** GraphQL で `rawPlainData` を取得。
5. **[UI]** カーソル位置に挿入。

### 9.3 `createSnippetPatch`(F3)

1. **[背景]** 対象リポジトリを解決。**HEAD コミットが無ければ中止**(VSCode も `assert`)。
2. **[背景]** 作業ツリー diff を生成。空なら「変更がありません」で終了。
3. **[UI]** パッチ名を入力(タイトルとファイル名に使う)。空/キャンセルで終了。
4. **[UI]** 可視性を選択。
5. **[背景]** タイトル `patch: <名前>` / ファイル名 `<名前>.patch` / 説明文(適用手順 + コミット記述子)で作成。
6. **[UI]** `web_url` をブラウザで開く。

### 9.4 `applySnippetPatch`(F4)

> **Codex レビュー反映(R1-1 / R1-2)**: 事前判定と適用の間の窓を閉じ、`PatchApplier` が原子的でない
> 前提で復元を設計する。

1. **[UI]** 早期の体験のための**予備チェック**: 対象リポジトリ配下に未保存のエディタがあれば、
   アラートを出して保存を促し、中止する(ユーザー判断・2026-08-12。自動保存はしない)。
   **これは体験上の早期中断であって、安全性の根拠ではない**(下記 5 が根拠)。
2. **[背景]** GraphQL で一覧取得 → `.patch` で終わる blob を持つものだけに絞る。0 件なら通知して終了。
3. **[UI]** スニペットを選択。
4. **[背景]** 内容を取得。
5. **[背景・排他境界の内側]** **JGit に作業ツリーを触らせない。**
   `PatchApplier` の worktree モードは書き込みを内部で行い、**呼び出し側が各書き込みを仲介できない**
   (第 3 巡 R3-1)。したがって**適用は in-core で行い、作業ツリーへの反映は自分で行う**。
   1. `GitOperationGuard` と、対象ファイルを覆う `ISchedulingRule` を取得する。
   2. **in-core 適用**: `PatchApplier(repo, HEAD ツリー, ObjectInserter)` で `applyPatch` する。
      このモードは**作業ツリーにも index にも触れない**。`Result.getErrors()` が空でなければ
      **何も変更せずに中止**する。空なら `Result.getTreeId()` が**適用後のツリー**になる。
   3. **HEAD ツリーと適用後ツリーを diff** し、変更集合を確定する
      —(パス, 変更種別, 新 blob id, **新ファイルモード**)。これが**書き込むべき全て**であり、
      JGit が勝手に書いたものではない。
   4. **index の事前ガード(第 4 巡 R4-2)**: 変更集合の各パスについて、
      **index が HEAD と異なる(= staged 変更がある)場合は適用前に中止**する。
      作業ツリーだけを見る照合は staged-only の変更を見逃し、7 の index 更新で**それを失わせる**。
   5. 変更集合の各パスについて、**書き込み直前に照合**する:
      作業ツリーの現在の内容ハッシュ・修正スタンプ・モードが**期待する適用前の値**と一致するか。
      一致しなければ**外部変更**とみなし、そのパスには書かず中止に入る。
   6. 一致したパスへ**自分で書き込む**(内容 + モード。実行可能ビットを含む)。
      書き込みは**同一ディレクトリの一時ファイルへ書いてから atomic rename** で置き換え、
      **rename の直前にもう一度ハッシュを読み直して照合**する(窓を最小化する)。
      **上書きする前の内容は必ず退避領域へ保存する**(下記「外部プロセスとの窓」)。
      書いたパスと**その post-image のハッシュ**を記録していく。
   7. 途中で失敗した場合、**自分が書いたパスだけを戻す**。戻す前にも照合するが、
      比較対象は**適用前の値ではなく 6 で記録した post-image** である
      —(適用前の値と比べると自分の書き込みで必ず不一致になる。第 3 巡 R3-1 の指摘)。
      post-image と一致しないパスは**外部で変更されたものとして戻さない**。
   8. 作業ツリーへの書き込みが**全て成功した場合にのみ**、index を更新する。
      **index ロックを取得した直後に、対象エントリが 4 で確認した基準状態のままであることを再検証**し、
      変化していれば index を更新せず中止する(第 4 巡 R4-2。作業ツリー反映後から
      index ロック取得前に外部 `git add` が入りうるため)。
      **index の更新を自分で行う**ため、JGit が index を書いた後に戻す形の競合(R3-6)は発生しない。
6. **[背景→UI]** 成功・復元いずれの場合も **`IResource.refreshLocal(DEPTH_INFINITE)`** を実行する
   (JGit はディスクを直接書くため、Eclipse のリソースツリーが古いままになる)。

**排他境界について(Codex レビュー第 2 巡 R2-1 で全面改訂)**

第 1 巡の反映時に書いた「残る窓で保存が起きても復元により**ユーザーの編集が失われない側に倒れる**」は
**誤りだった**。スナップショット取得後に対象ファイルが保存され、その後に後続ファイルの適用が失敗すると、
**復元が新しい保存内容を古いスナップショットで上書きして破壊する**。さらに適用後 refresh 前の保存は、
JGit が成功していても**パッチ側を上書き**する。検出型だけでは閉じない。

したがって、次の**二重の防御**を設計に組み込む。

1. **排他を適用・復元・refresh まで保持する。** 対象ファイルを覆う `ISchedulingRule` を取得し、
   `IWorkspace.run(...)` の内側で「in-core 適用 → 書き込み → 復元判定 → refresh」を実行する。
   Eclipse の保存はワークスペースを経由するため、この区間の保存は待たされる。
   `GitOperationGuard` は**git 操作の直列化専用**であり、この排他の代わりにはならない。
2. **書き込みのたびに照合する。** §9.4-5/7 のとおり、書き込む直前に現在の内容ハッシュ・
   修正スタンプ・モードを照合し、一致しなければ**その書き込みを行わない**。
   **これは外部プロセスに対する CAS ではない**(§9.4.1)。窓の最小化と退避による可復元性で担保する。
   **外部の変更を上書きするくらいなら、作業ツリーが中間状態のまま残るほうを選ぶ**。
   その場合は「一部のファイルは外部で変更されたため復元しませんでした」と対象件数を通知する
   (パスは出さない — §16)。

1 だけでは Eclipse 外からの書き込み(外部エディタ・他ツール)を止められず、2 だけでは
チェックと書き込みの間の窓が残るため、**両方を要求する**。

### 9.4.1 外部プロセスとの窓は「CAS」ではない — 縮小と可復元性で担保する(第 4 巡 R4-1)

第 3 巡の記述は照合と書き込みを「CAS」と呼んでいたが、**これは正確ではない**。
`ISchedulingRule` が待たせるのは **Eclipse を経由する保存だけ**であり、
外部エディタや他プロセスの書き込みは止められない。したがって照合と書き込みの間の窓は、
**現在の Eclipse / Java のファイル API では原理的に消せない**(POSIX の advisory lock は
一般的なエディタが取得しないため実効性がない)。**「CAS である」と主張しない。**

代わりに、**窓を最小化し、最終照合時点の内容を退避しておく**ことで担保する。
**「窓に当たっても失わない」とは主張しない**(第 6 巡 R6-5)— 訂正版 A18 と §22 のとおり、
最終照合後に外部が保存した内容は失われ、検出もできない。ここでの保証範囲は
**「最終照合時点の内容が退避されていること」**に限る。

1. **窓の最小化**: 一時ファイルへ書いてから **atomic rename** で置換し、
   **rename 直前に再度ハッシュを読み直して照合**する。照合と置換の間隔をシステムコール 1 回分にする。
2. **可復元性(こちらが本質)**: **上書き・削除する前の内容を必ず退避領域へ保存する。**
   退避先はプラグインの state ディレクトリ配下とし、パッチ適用ごとに 1 つのフォルダにまとめる。
   **保証するのは「最終照合時点の内容が退避されていること」までである**(下記 A18 訂正版)。
   **「窓に当たっても失わない」とは主張しない。**
3. **告知**: 適用が中止・復元された場合、および退避を行った場合は、
   **退避領域の存在と対象件数を通知する**(パスは出さない — §16)。

**削除・rename 元のパスにも同じ窓がある(第 6 巡 R6-6)**: 変更集合には DELETE と rename 元が含まれ、
これらは rename による置換ではなく**削除操作**になる。削除も**最終照合 → 削除**の順であり、
その間に外部プロセスが保存した内容は**そのまま消える**。退避は削除前に行うが、
**窓に入った書き込みは退避に含まれない** — 置換の場合とまったく同じ既知の制限として扱い、
§22 のリスク表と A18 の対象に**削除パスも含める**。

### 9.4.2 退避領域の寿命と上限(第 5 巡 R5-3)

「一定期間」「古いものから削除」だけでは、**唯一のコピーが復元前に消える**ことも
**state ディレクトリを無制限に消費する**ことも防げない。次を規定する。

| 項目 | 規定 |
|---|---|
| 最低保持期間 | この期間内の退避は**削除しない**。上限に達したときは、**まず最低保持期間を過ぎた退避を古い順に削除して容量を確保**する。それでも確保できない(= 期間内の退避しか無い)場合に限り、**新しい退避を作らず適用を中止**する(古いものを消して進むより安全側)。受け入れ条件は A21 の (a)/(b) に分岐する(第 6 巡 R6-4) |
| 総容量・件数の上限 | 容量と件数の**両方**に上限を置き、**先に到達したほうで判定**する |
| 削除順序 | 最低保持期間を過ぎたものを**古い順**に削除する |
| 削除前の通知 | 削除するときは**件数を通知**する(パスは出さない) |
| 起動時・異常終了後の清掃 | 起動時に退避領域を走査し、**最低保持期間を過ぎたものを削除**する。適用中にプロセスが落ちて残った退避は、**完了マーカーが無いものとして保持**し、ユーザーに存在を知らせる |
| 単一適用が上限を超える場合 | **適用を開始しない**(退避できない状態で書き込まない) |

具体的な値(最低保持期間の日数、容量・件数の上限)は **U8** として実装計画で確定する。
**境界試験**(上限到達・最低保持期間内での上限到達・起動時清掃)を受け入れ条件 **A21** に含める。

**残る窓は「捕捉できない」— 受け入れ条件を正確に書き直す(第 5 巡 R5-1)**

第 4 巡で書いた A18「外部プロセスが保存しても退避領域から復元できる」も、**まだ強すぎた**。
退避コピーの取得(および最終ハッシュ照合)から rename までの間に外部保存が入ると、
**その新しい内容は rename で上書きされ、退避領域には窓より前の内容しか無い**。
Java からは `renameat2(RENAME_EXCHANGE)` 相当の **atomic exchange を呼べない**ため、
置換対象を同時に保持する方法が無い。

したがって A18 を**保証できる範囲に訂正する**。

> **A18(訂正版)**: 適用によって**上書きまたは削除**される各パスについて、
> **最終照合時点の内容が退避領域に保存されていること**。
> **最終照合から実際の置換 / 削除までの窓(システムコール 1 回分)に書き込まれた内容は捕捉できない** —
> これは既知かつ受容する制限であり、§22 のリスク表に記載する。
> 置換(rename)と削除の**両方**が対象である(第 6 巡 R6-6)。

**この制限の実際の露出**:

- **Eclipse を経由する保存は `ISchedulingRule` により待たされる**ため、この窓には入らない。
- 対象は**外部エディタ・他プロセスによる書き込みのみ**で、窓は最終照合と rename の間に限られる。
- 窓に当たった場合、**その書き込みは失われる**。検出もできない(rename 後に比較しても
  上書き後の内容しか読めない)。**「起きない」とも「必ず戻せる」とも書かない。**

**この 2 が成立するのは、§9.4-5 で「書き込みを自分で行う」設計に切り替えたから**である
(第 3 巡 R3-1)。JGit の worktree モードに適用させたままでは、**各書き込みを仲介する手段が無く
2 は実装できない**。照合の基準が「適用前」ではなく**自分が書いた post-image** である点も同じ理由による。

### 9.6 `publishToGitLab`(F6)

> **Codex レビュー反映(R1-4 / R1-5 / R1-6 / R2-1)**: 破壊的操作をすべてユーザー入力の**後**に寄せ、
> 初期コミットを定義し、push の成否を `RemoteRefUpdate.Status` で判定し、push 失敗から再開できるようにする。

**フェーズ 0 — 前提の判定(読み取りのみ。ファイルシステムを変更しない)**

1. **[UI]** ワークスペースプロジェクトを選択(複数時)。
2. **[背景]** 対象の状態を判定する。**この時点では `init` しない**(R2-1: キャンセルしただけで `.git` が
   残るのは N5 違反)。
   - 既に remote がある → **原則中止**。ただし**再開条件**(下記フェーズ 3)に合致する場合のみ続行。
   - リポジトリだが **detached HEAD** → 中止(push すべきブランチが定まらない)。
   - リポジトリでもディレクトリでもない、または**追跡対象になりうるファイルが 0 件** → 中止。

**フェーズ 1 — 入力(まだファイルシステムを変更しない)**

3. **[UI]** 名前空間・プロジェクト名・**可視性(既定 private)**・接続方式(SSH/HTTPS)を入力。
4. **[UI]** **最終確認**。非リポジトリの場合は「`git init` して**全ファイルを初期コミットする**」ことと、
   **コミット対象のファイル数**を明示する。`.gitignore` が無い場合は
   **「除外設定が無いためすべてのファイルが公開されます」と警告**する(秘密情報の混入防止)。
   ここまでのキャンセルでは**ファイルシステムは一切変化していない**。

**フェーズ 2 — ローカル準備(ここから破壊的)**

5. **[背景]** 非リポジトリなら `init` → `AddCommand.addFilepattern(".")`(**`.gitignore` を尊重する**)
   → `Initial commit` をコミットする。既存リポジトリで**コミットが 0 件**の場合も同様に初期コミットを作る。

**フェーズ 3 — リモート作成と push**

6. **[背景・R2-3]** **`POST /projects` を出す前に `PublishIntent` を永続化する**
   (リポジトリ識別子・名前空間・パス)。POST 成功後に記録する順序では、**応答受信後のプロセス終了、
   preference 保存失敗、応答断**のいずれかで「GitLab にプロジェクトはあるが記録も remote も無い」状態になり、
   次回は再開条件に入らず新規作成へ進んで**プロジェクトが孤立し、二重作成もできてしまう**。
7. **[背景]** `POST /projects` に `{path, namespace_id, visibility}`。
8. **[背景]** 応答を受けて `PublishIntent` を **`PublishState` へ確定遷移**させる(§11)。
   **intent の破棄と state の書き込みは同一のロック下で一度に行う**(中間状態を残さない)。
9. **[背景]** remote を追加し、現在のブランチを push する。
   **成否は `call()` が返ったことではなく、既存 `BranchPushService.doPush` と同じ判定による**
   (R1-6): JGit は protected branch や non-fast-forward を例外にせず `PushResult` の
   `RemoteRefUpdate.Status` で返す。**全 transport の対象 ref が `OK` または `UP_TO_DATE` の場合のみ成功**とし、
   **upstream 設定はその後に行う**。判定ロジックは新規に書かず既存実装を共有する。
9. **[UI]** 結果を通知。

**再開(R1-5 / R2-3 / R2-4)**: push だけが失敗した場合、作成済みプロジェクトと追加済み remote は
**残す**(§12)。再実行時、フェーズ 0 の「remote があれば中止」に**例外**を設ける —
**確定済み `PublishState` が存在し、既存 remote がその記録と一致する場合に限り**、
**プロジェクトを作らずに push だけを再試行**する。一致しなければ従来どおり中止する。
成功したら記録を破棄する。

一致判定は **`remoteName` と `projectWebUrl` では成立しない**(R2-4)。特に SSH を選んだ場合、
web URL から SSH の user / host / port を一意に復元できず、緩いパス比較は取り違えを招く。
したがって `PublishState` には**実際に追加した remote URL を正規化して保存**し、
`instanceUrl` と **GitLab の project ID** も併せて保存する(§11)。判定はこの正規化 URL の一致で行う。

**未確定 intent の回復(R2-3 → 第 3 巡 R3-2 / R3-3 で厳格化)**

再実行時に `PublishRecord = Intent` が残っていた場合の扱い。**「パスが存在する = 前回の POST が作った」
とは判定しない**(R3-3)。既存パスとの競合で POST が失敗した場合や、応答不明の間に別ユーザーが同じパスを
作った場合、その既存プロジェクトを前回の成果と誤認して push しうるため。

1. **インスタンス照合**: 記録の `instanceUrl` が現在の接続と一致しなければ、**回復を試みない**。
   記録は残したまま、通常フローも行わずに中止し、状況を通知する(R3-2)。
2. **既知の失敗は破棄**: 直前の POST が**明確な失敗**(パス重複などの 4xx)で終わっていた場合、
   intent を破棄して通常フローを続行する。
3. **応答不明のときのみ照会**する。照会でプロジェクトが見つかった場合でも自動採用はせず、
   **所有関係を確認できるときのみ採用**する — **作成者が現在のユーザー**であり、かつ
   **プロジェクトの作成時刻が `Intent.recordedAt` の近傍**にあること。
   **`recordedAt` は Intent に永続化する**(第 4 巡 R4-6。無ければこの条件は評価できず、
   毎回ユーザー確認に落ちるか、時刻条件を省いて誤採用することになる)。
   - **許容幅**は「記録時刻 − 猶予 〜 現在時刻 + 猶予」とし、猶予は**クライアントとサーバの
     時計ずれを吸収する固定値**とする(値は U6 と併せて実装計画で確定する)。
   - サーバ時刻を信頼できないため、**この条件は単独では採用根拠にせず、作成者一致と併用**する。
   - 範囲外なら 4 のユーザー確認に落とす(**誤採用より確認を選ぶ**)。
4. **確認できない・曖昧な場合はユーザーに確認する。** 「このプロジェクトは前回の実行で作成されたものですか」
   を提示し、**明示的な同意が無ければ push しない**。同意が無ければ intent を破棄して通常フローに戻す。

**冪等性の根拠**: 3 の所有確認と 4 の明示同意により、応答が失われても
「二重作成」も「他人のプロジェクトへの push」も起きない。

## 11. データモデル

- `SnippetSummary(id, title, description, blobs: List<SnippetBlob>)`
- `SnippetBlob(name, path, rawPath)`
- **`ProjectAssignment(repositoryRootPath, remoteUrl, instanceUrl, namespaceWithPath, projectId)`**
**発行の永続記録は、リポジトリごとに「1 つの値」として保存する**(第 3 巡 R3-4)。
intent の削除と state の書き込みを別々の書き込みにすると、**同一ロックはスレッド間の排他にしかならず、
削除後・書き込み前のクラッシュや flush 失敗で両方消える(または逆順で両方残る)**。
単一の値を**置換**すれば、遷移は 1 回の書き込みになりクラッシュ回復可能になる。

```
PublishRecord =
  | Intent(repositoryRootPath, instanceUrl, namespacePath, projectPath, recordedAt)
  | State (repositoryRootPath, instanceUrl, namespacePath, projectPath,
           projectId, normalizedRemoteUrl, remoteName, projectWebUrl)
```

- **`instanceUrl` は Intent の段階から必須**(第 3 巡 R3-2)。これが無いと、インスタンス A で応答を失った後に
  B へ切り替えたとき、**B に同じ namespace/path があれば回復処理が B のプロジェクトを誤採用**する。
  `PublishState` にだけ持たせても、**未確定 intent の照会前には使えない**ため意味がない。
  現在の接続と一致しない記録は**自動回復しない**。
- **`normalizedRemoteUrl` / `projectId` は再開の一致判定に必須**(R2-4)。
  `projectWebUrl` は通知用であって判定には使わない — SSH remote を web URL から復元できないため。
- 万一 Intent と State の両方が観測された場合(実装ミスや外部編集)、**State を優先**する。
- `SelectedProjectStore` の永続先は既存 `ScopedPreferenceStore`(**新規の設定ファイルは作らない**)。
  複数割当を 1 キーに収めるため、区切り文字ではなく**構造化した文字列**(JSON 相当)を 1 値に入れる。
  **区切り文字方式は remote URL に任意文字が入りうるため採らない。**

### 11.1 割当のインスタンス束縛(Codex レビュー反映 R1-3)

**`instanceUrl` は必須**。これが無いと、インスタンス A で保存した割当が、設定を B に変えた後も
そのまま使われる。デコレータは既存 `GitLabProjectUrlResolver` の**前**に立つため、
resolver が行う「remote と設定インスタンスの照合」を**迂回してしまう**。その状態で
`namespaceWithPath` / `projectId` を B に対して使うと、**同名・同 ID の別プロジェクトへ書き込みが向かう**
(スニペット作成・プロジェクト作成など)。

したがって `AssignedProjectResolver` は、割当を採用する前に**次の 2 つを検証し、いずれかが
一致しなければその割当を無効として既存 resolver に委譲する**:

1. 割当の `instanceUrl` が**現在の接続インスタンスと一致**する(正規化して比較。
   既存 `GitAuthConfigurer.hostMatchesInstance` と同じ「scheme + host + 実効ポート」の基準を使う)。
2. 割当の `remoteUrl` が**対象リポジトリに現存する remote と一致**する。
3. **(R2-4 で追加)割当の `remoteUrl` 自身が、その `instanceUrl` のインスタンスに属する。**

**条件 3 が無いと穴が残る**(Codex レビュー第 2 巡 R2-5): 1 と 2 だけでは
「保存された `instanceUrl` が現在の接続と一致」かつ「その remote が現存する」しか見ておらず、
**remote が別インスタンス A や GitHub のものであっても両条件を通過する**。その状態で
デコレータが当該リポジトリを B 上の割当プロジェクトとして解決すると、**書き込みが誤送信される**。

条件 3 の判定は**両方のリモート形式**を扱う。

- **HTTPS**: `GitAuthConfigurer.hostMatchesInstance(remoteUrl, instanceUrl)` をそのまま使う
  (scheme + host + 実効ポート)。
- **SSH / scp-like**(`ssh://user@host:port/path` / `git@host:path`): host と**明示ポート**を取り出して
  照合する。scheme は比較対象にしない(SSH と HTTPS で必ず異なるため)。

> **既存 `GitLabRemoteParser` に委ねてはいけない**(第 3 巡 R3-5・実コードで確認)。
> 第 2 巡では「既存 `GitLabRemoteParser` と基準を揃える」と書いたが、これは**誤り**だった。
> 同ファイルの冒頭コメント(`GitLabRemoteParser.kt:18`)が
> 「Behavior (incl. quirks: **dropped SSH ports**, ...) is preserved verbatim」と明記しているとおり、
> `normalizeSshRemote` は **SSH の明示ポートを落とす**。さらに
> `remoteMatchesInstance`(`:42-48`)は `if (instProtocol != remote.protocol && instHostname != remote.hostname) return false`
> であり、**scheme が異なる場合は hostname のみの比較**に退化する。
> このまま委ねると、**同じ host の別 SSH ポートで動く別サービス**が条件 3 を通過する。
>
> したがって条件 3 用に、**SSH authority をポート込みで保持する専用のパース**を持つ。
> `GitLabRemoteParser` は VSCode 版の挙動を忠実に移植したものなので**変更しない**
> (他機能の URL 解決がその挙動に依存している)。
>
> **GitLab の SSH ポートは HTTPS の実効ポートとは独立**であり、`instanceUrl` からは決まらない。
> 照合規則は「remote の host が instance の host と一致すること」を必須とし、
> **ポートは、設定に GitLab の SSH ポートが与えられている場合のみ照合する**。
> 与えられていない場合はポートを判定に使わず、**host 一致のみで通す**(過剰拒否を避ける)。
> この設定項目の要否は **U7** として未決に置く。

無効化は**黙って行わず**、解決結果の Warn として「割当が現在のインスタンスと一致しないため使用しません」を返す。
- スニペット一覧は**先頭ページのみ**を扱い、`hasNextPage` が true のときは
  「一部のみ表示しています」を UI に出す(黙って切り捨てない)。

## 12. トランザクション境界

本機能に分散トランザクションは無いが、**部分的に成功して戻せない操作**が 2 つある。

| 操作 | 部分成功のしかた | 扱い |
|---|---|---|
| `publishToGitLab` | プロジェクトは作成されたが push に失敗 | **作成したプロジェクトも remote も削除しない。** 「プロジェクトは作成されましたが push に失敗しました」と明示し、リモート URL を通知する。**`PublishState` を残し、次回実行で push だけを再開する**(§9.6・R1-5) |
| `applySnippetPatch` | パッチが部分適用される | **`PatchApplier` は原子的ではない**(下記)。in-core 事前検証 + スナップショット復元で対処する(§9.4) |

### 12.1 `PatchApplier` の非原子性(Codex レビュー反映 R1-1・実バイナリで確認)

当初 §12 に書いていた「JGit `ApplyCommand` は全適用か例外か」という前提は**誤り**だった。
同梱される JGit 7.5.0(`org.eclipse.jgit-7.5.0.202512021534-r.jar`)の API を確認した結果:

```
public class org.eclipse.jgit.patch.PatchApplier {
  public PatchApplier(Repository);
  public PatchApplier(Repository, RevTree, ObjectInserter);   // ← in-core(作業ツリーに触れない)
  public PatchApplier$Result applyPatch(Patch) throws IOException;
}
public class org.eclipse.jgit.patch.PatchApplier$Result {
  public List<String> getPaths();
  public ObjectId getTreeId();
  public List<PatchApplier$Result$Error> getErrors();          // ← エラーは「収集」される
}
```

**結果型がエラーの一覧を返す時点で、「全適用か例外か」ではない。** 複数ファイルのパッチで
後続ファイルが衝突・I/O エラーになっても、先行ファイルへの書き込みは既に済んでいる。

**したがって、これを実装時の確認事項(旧 U2)にはせず、設計上の前提として扱う。** 対策は §9.4 のとおり:

1. **in-core コンストラクタ**(`Repository, RevTree, ObjectInserter`)で**先に検証**する。
   このモードは作業ツリーを一切書き換えない。`getErrors()` が空でなければそこで中止する。
2. それでも作業ツリーへの適用は非原子的なので、**対象パスをスナップショットしてから適用し、
   途中失敗時は復元**する。復元時の上書き防止は §9.4 の二重防御に従う。
3. 受け入れ条件に**「途中で失敗するパッチを適用しても作業ツリーが元に戻る」**テストを含める(A11)。

### 12.2 index(DirCache)を JGit に触らせない(第 2 巡 R2-2 → 第 3 巡 R3-6 で方式変更)

**第 2 巡での確認**: 同梱 JGit 7.5.0 の `PatchApplier` を `javap -p -c` で調べたところ、
worktree モードでは **`lockDirCache` を呼び `DirCacheBuilder.commit` を実行**している。
つまりエラーを収集した後でも **index への変更は確定する**。当初はこれを「index もスナップショットして
復元する」で対処しようとしたが、**JGit が index ロックを解放してから復元用に再取得するまでの間に
外部の `git add` が入ると、その staged 変更を上書きしてしまう**(第 3 巡 R3-6)。

**したがって復元ではなく回避に切り替える。** §9.4-5 のとおり適用は **in-core モード**で行う。
in-core は作業ツリーにも index にも触れないため、**JGit が index を書くこと自体が起きない**。
index の更新は**作業ツリーへの書き込みが全て成功した後に、こちらが行う**。
これで「JGit が書いた index を後から戻す」という競合の余地が構造的に消える。

**スナップショット(復元用)に含めるもの** — 対象は作業ツリーのみ:

- 対象パスの**ファイル内容**(または不存在であること)
- 対象パスの**存在種別**(通常ファイル / シンボリックリンク / 不存在)
- **ファイルモード。とくに POSIX 実行可能ビット**(第 3 巡 R3-8)。
  `100644` と `100755` を「通常ファイル」とまとめると、mode だけ変更後のまま残る。
  自分で書き込む設計では、モードは適用後ツリーのエントリから取って設定し、復元時も元の mode に戻す。

**A11 は「作業ツリーの内容・モード・index が適用前に戻る」ことを検証する**(mode 変更を含むパッチと、
実行可能ビットのみを変えるパッチの両方を対象にする)。

## 13. エラー処理

- 既存の `Resolution.Warn(message)` / 通知パターンに揃える。**例外をユーザーに素通ししない。**
- **JGit の例外メッセージはリモート URL を含みうる**ため、そのまま通知・ログに流さない。
  ユーザー向けは定型文、ログは**例外の型名のみ**。
- REST/GraphQL の失敗は既存 `GitLabApiException` / `GraphQlException` の扱いに従う。
- キャンセル(ダイアログを閉じる)は**エラーではない**。無言で終了する。

## 14. タイムアウト・リトライ・冪等性

- **タイムアウト**: REST/GraphQL は既存 `GitLabHttpClient` の設定に従う。

**git 操作のキャンセルとタイムアウト(Codex レビュー反映 R1-7)**

当初の「`IProgressMonitor` 付き Job に入れるのでキャンセルできる」は**不十分**だった。
Eclipse の Job が monitor を持っていても、**ブロッキング中の JGit transport は止まらない**。
本プラグインは EGit UI に依存しないため `EclipseGitProgressTransformer` も使えない。したがって:

1. **アダプタを自前で持つ**: `org.eclipse.jgit.lib.ProgressMonitor` を実装し、Eclipse の
   `IProgressMonitor` に委譲する小さなクラスを作る。**`isCancelled()` が Eclipse 側のキャンセルを返す**
   ようにし、`CloneCommand` / `PushCommand` に `setProgressMonitor(...)` で必ず設定する。
2. **有限のタイムアウトを設定する**: `TransportCommand.setTimeout(seconds)` で接続・読み取りに上限を置く。
   progress callback に到達しない状態(接続が張れない等)は `isCancelled()` では抜けられないため、
   **タイムアウトが最後の砦**になる。既定値は設計上の定数として定め、設定では露出しない。
3. **後始末を定義する**: キャンセル/タイムアウト時、
   - **clone(R2-7 → 第 3 巡 R3-7 で方式変更)**: 第 2 巡では「コマンドが作成した子要素だけを削除」
     としたが、**`CloneCommand` が内部で作ったパスを呼び出し側から識別できず**、
     clone 中に別プロセスやエディタが作った同名の子要素まで消しうる(R3-7)。
     **識別に頼るのをやめ、隔離する。**
     **一時ディレクトリ + atomic move はやめ、「予約」方式に変更する(第 5 巡 R5-2)。**

     Java の `ATOMIC_MOVE` は**宛先が存在するときの置換可否が実装依存**で、
     **Linux では既存の空ディレクトリを置換できる**。したがって「事前に存在確認 → 転送 → move」では、
     確認後に競合で作られた空ディレクトリやシンボリックリンクを**消して置き換えてしまう**。
     事前確認と move の間の窓は閉じられない。

     - **開始時に `Files.createDirectory(宛先)` で宛先を予約する。**
       この呼び出しは**原子的で、既に存在すれば失敗する**(no-replace)。
       Java から使える**唯一の原子的な no-replace プリミティブ**であり、
       ディレクトリ move には同等の保証が無い(`ATOMIC_MOVE` は置換可否が実装依存)。
     - **clone は宛先直下の専用ステージング用サブディレクトリへ行う**(第 6 巡 R6-1)。
       予約が保証するのは**ディレクトリ自体の作成者**だけで、**以後の全子要素の所有者ではない**。
       予約先は**ユーザーから見える場所**なので、clone 中に同期ツールやエディタが
       そこへファイルを作りうる。**ステージング用サブディレクトリの名前は本コマンドしか知らない**ため、
       **その配下は構造的に全て自分の生成物**になる。
     - 成功時は、ステージング配下を**宛先直下へ移して**ステージングを削除する。
     - **後始末の規則(外部作成物を消さない)**:
       1. **ステージング用サブディレクトリは常に丸ごと削除する**(全て自分の生成物のため)。
       2. その後、**宛先が空のときに限り宛先も削除する**。
          空でなければ**外部が書き込んだものが残っている**ということなので、**宛先は削除せず残し**、
          その旨を通知する(パスは出さない — §16)。
     - ユーザーが既存のディレクトリを選んだ場合は予約が失敗する。
       **その配下の新規サブディレクトリを提案**するか選び直してもらう(**削除はしない**)。
     - **異常終了への備え(第 6 巡 R6-2)**: 予約に成功した時点で
       **`CloneReservation(destPath, stagingName, recordedAt)` を永続化**する。
       clone 成功・後始末完了のいずれでも記録を破棄する。
       **起動時に記録が残っていれば**、上記の後始末規則 1→2 を適用して回復し、記録を破棄する。
       宛先が空でなく残った場合は**ユーザーに存在を知らせる**。
       これが無いと、A6 が既存宛先を常に拒否するため、**部分的な `.git` を含む宛先を
       次回実行で再開も除去もできなくなる**。
   - push: 追加済み remote は**残す**(§9.6 の再開経路が使う)。
4. `GitOperationGuard` の占有は上記により有限時間で解放される。**無応答 transport を使った
   タイムアウト/キャンセル試験を受け入れ条件に含める**(A12)。
- **リトライ**: **自動リトライは行わない。** 作成系(スニペット作成・プロジェクト作成)は**冪等ではなく**、
  自動再試行は重複を生む。失敗はユーザーに提示し、再実行の判断を委ねる。
- **冪等性**:
  - スニペット作成・プロジェクト作成: **非冪等**(同名で複数作成されうる)。二重押し防止のため
    実行中はコマンドを無効化する。
  - `applySnippetPatch`: **非冪等**(同じパッチの二度適用は失敗する)。失敗を正常な結果として扱う。
  - `selectProject`: **冪等**(同じキーへの上書き)。

## 15. 並行処理

- git 操作は既存 `GitOperationGuard` で**リポジトリ単位に直列化**する。clone/push/apply すべて対象。
- **UI スレッド境界**: エディタ本文・選択範囲の読み取り、テキスト挿入、ダイアログは**UI スレッド必須**。
  REST/GraphQL/JGit は背景。既存 `WorkspaceProjectPicker` の形
  (**UI で読む → coroutine → 必要なら `asyncExec` で戻る**)を踏襲する。
- 例外がコルーチンから漏れると**共有 plain-Job スコープが道連れで停止する**(#16 で確認済み)。
  すべての `launch` で `CancellationException` は再送出、それ以外は封じ込める。

### 15.1 `SelectedProjectStore` の更新は原子的に行う(Codex レビュー反映 R1-8)

当初は「読み取りはスナップショットを返す」しか定めていなかったが、**複数割当を単一の JSON 値に
収める設計では書き込み側の read-modify-write にも排他が要る**。異なるリポジトリに対する
`selectProject` が 2 件並行して完了すると、双方が同じ旧 JSON を読み、後勝ちの保存で**一方の割当が消える**。

- **読み取り・更新・preference への永続化を同一のロック下**で行う(`Mutex` または同期ブロック)。
- 公開スナップショットは**確定した状態から**更新する(ロック内で確定 → 参照を差し替える)。
- **永続化が失敗したらスナップショットを更新しない**(R2-8)。書き込みまたは flush が失敗した場合、
  メモリ上だけ成功したように見える状態を作らない。**「同一セッション中は効くが再起動で消える」は
  A7 と矛盾する**ため、順序は必ず「永続化成功 → スナップショット差し替え」とする。
  受け入れ条件 **A17**、および**書き込み失敗を注入する試験**を定める。
- **flush 失敗時は preference の値自体も旧 JSON へ戻す**(第 3 巡 R3-9)。
  `ScopedPreferenceStore` は `setValue` した時点で**ストアのメモリ状態が変わる**ため、
  スナップショットを据え置くだけでは新値がストア内に残り、**後続の別保存や終了時 flush で
  「失敗として通知した割当」が永続化されうる**。したがって**ロックを解放する前に**
  preference の値を旧 JSON へ書き戻し、以後の read-modify-write が
  **確定スナップショットだけを基点**にすることを保証する。A17 にこの条件を含める。
- 受け入れ条件に**「異なるキーへの並行保存後、両方の割当が残る」**テストを含める(A13)。

### 15.2 パッチ適用の排他境界

§9.4 のとおり、`GitOperationGuard` はプラグイン内の git 操作しか排他しない。エディタの編集・保存は
止められないため、**再検証(dirty + 修正スタンプ)→ 適用 → 復元判定 → refresh** を一連の区間として扱い、
区間の入口で状態が変わっていれば中止する。**「止める」のではなく「検出して中止し、必要なら戻す」**設計。
