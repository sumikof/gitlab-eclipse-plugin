# Secret redaction mechanism — design

対象 issue: #54(`data class` の生成 `toString()` が資格情報を載せている件)
ベースブランチ: `develop` @ `0ea03e6`
関連実装 PR: なし(本設計のレビュー完了後に作成)

---

## §1 背景と目的

Phase 6 優先 1(webview 面の開放・PR #55)のブランチ全体レビュー中に、同種の欠陥が
リポジトリ全体に残っていることが判明した。当該 PR のスコープを広げないため #54 として切り出した。

**欠陥の形**: Kotlin の `data class` は `toString()` を自動生成し、全成分を文字列形に出力する。
秘匿すべき成分(資格情報・ユーザーのファイルパス・例外メッセージ)を持つ `data class` が
`toString()` を上書きしていない場合、その値が文字列形に載る。

**現時点ではいずれも live ではない。** 対象クラスを丸ごと補間しているログ行は存在しない(§4.2 で実測)。
ただしこれは規律であって機構ではない。1 箇所の `logger.debug("$token")` で live になる。
`GitLabAuthorizationToken` は、Phase 4 PR-4 の Codex P1-1 で実際に起きたインシデント
(例外添付経由で `Bearer <token>` が Error Log に漏れた)とまったく同じ形をしている。

**目的**: 秘匿値が生成 `toString()` に載らないことを、**規律ではなく機構で**担保する。
機構の要件は「今ある違反を閉じること」ではなく「**次の違反を止めること**」である。

## §2 対象範囲

1. 秘匿成分を持つ `data class` の `toString()` 上書き(§6 の 12 クラス)。
2. その性質をリポジトリ全体に対して固定する規約テスト 1 本(§7・§8)。
3. 各 `toString()` の出力形を固定するクラス単位テスト 12 本(§9・§21)。

## §3 対象外

| 対象外 | 理由 |
|---|---|
| 41 件の `data class` すべてへの `toString()` 上書き | #54 自身が「41 個の手書き上書きは対処にならない / 42 件目を止めるものが何も無い」と論じている。内訳の大半は秘匿を何も運ばない |
| フィールド型のラッパー型(`SecretString` 等)への置換 | §16.2 に却下理由 |
| 明示注釈(`@Secret` 相当)の導入 | 本フェーズで印を付ける対象が新規に存在しない(既存の該当 6 件は PR #55 で閉じ済み)。使われない機構を先に建てることになる。結果として生じる穴は L-1 |
| 非 `data class` の手書き `toString()` | L-2 |
| 秘匿値への到達可能性の推移閉包(保持クラス・コンテナの型引数まで検出すること) | §7.6。停止点が無い。結果として生じる穴は L-5 |
| **ハーネス自身をテストで固定する層** | **§8.4。テストコードは差分レビューが守る。結果として生じる穴は L-7** |
| detekt カスタムルール | 閾値設定ファイル(`detekt.yml`)の変更を伴い、共通制約「ビルドシステムの変更禁止」と調整が要る。規約テストは同じ担保をビルド設定に触れずに与える |

## §4 現在の課題

### §4.1 実測した現況

`src/main/kotlin` 配下、`data class` 158 件。既存の `toString()` 上書きは 8 件
(`WebviewInfo` / `ProxyConfig` / `PluginMessageRoute` / `Outcome.Show` / `WebviewResolution.Resolved` /
`WebviewResolution.Failed` / `WebviewEditorKey` / `ActiveYamlEditorUri.Resolved`)。
このうち 6 件は PR #55 で「クラスとして閉じる」作業として追加されたもの。

### §4.2 live ではないことの確認

対象クラスを丸ごと補間しているログ行を掃いた結果、production に該当なし。
`GitLabLanguageServerProcessProvider.kt:179` の `$result` は lsp4j の `InitializeResult`、
`:332` の `$key` は環境変数名の文字列で、いずれも本設計の対象型ではない。

**ただし「補間されていない」は強制されていない性質である。** 実際に `data class` を丸ごと補間している
ログは他に実在し(`CiLintLaunch.kt:123` / `DisplayJobLogHandler.kt:168` の `$key`)、
そのうち `JobLogKey` は資格情報を**意図的にハッシュ化**することで「補間しても安全」を
個別の判断で担保している。判断が要る状態そのものが課題である。

### §4.3 #54 の記述に対する訂正・補足

1. **#54 が挙げた資格情報 4 件のほかに、`EgressConfigSnapshot`(CA 証明書・クライアント証明書・
   クライアント鍵の**ユーザーファイルパス** 3 成分)と `HttpAgentOptions`(`cert` / `certKey`)がある。**
2. **`HttpAgentOptions` は `GitLabLanguageServerConfigurationParams` の入れ子である。**
   外側に `toString()` を書いて `token` を伏せても、`httpAgentOptions` を印字すれば
   入れ子の生成 `toString()` 経由で `certKey` が出る。「外側だけ直す」が効かない実例。
3. `data class` 総数は 158 件(#54 の記載は 149 件。PR #55 のマージで増えている)。

## §5 要件

- **R1**: 秘匿成分を持つ `data class` の `toString()` 出力が、**その成分の値に依存しないこと**。
  「値が出力に現れないこと」ではない — それでは `Base64` 等で符号化した可逆な漏洩を許す(§7.3)。
  **ただし A1 が検査するのは有限個の標本であり、値への依存を一般には否定できない**(L-8)。
- **R2**: 新たに秘匿成分を持つ `data class` が追加されたとき、`toString()` を上書きしない限り
  ビルドが失敗すること(= 42 件目を止める)。
- **R3**: 検出器が対象を見落とした場合に、それが「違反ゼロ」として観測されないこと。
- **R4**: 各 `toString()` が何を出力するかが固定されていること(R1 を満たすだけの空文字列等に
  退化していないこと)。
- **R5**: 障害調査に必要な情報(例外の型、接続先インスタンス、認証フィンガープリント等)が
  `toString()` から失われないこと。

## §7 検出規則

### §7.1 走査対象

`KClass.isData == true` の Kotlin クラスのみ。

**非 `data class` を対象にしない理由は 2 つある。**

1. 本設計が閉じる欠陥は「**生成された** `toString()`」である。非 `data class` の既定 `toString()` は
   `Any` 由来の同一性ベースで、成分の値を出力し得ない。
2. 名前パターンは非 `data class` のフィールドにも当たる
   (`OAuthTokenProvider.currentToken` / `GitLabApiClient.tokenManager` /
   `SecurityScanLauncher.tokenProviderManager` / `SidebarRefreshCoordinator.assignedKey` /
   `OAuthSecretStorage.secretStorage` 等)。これらはサービス実体であり §7.4 の組み立てが
   成立しない。A6(組み立て不能は失敗)と組み合わせると、対象に含めた時点でビルドが落ちる。

### §7.2 秘匿フィールドの判定

**クラスにではなくフィールドに印を付ける。** あるフィールドが秘匿を運ぶとは、次の**いずれか**に当たること:

- **D1**: フィールド名が次のいずれかを大小無視の部分一致で含む —
  `token` / `secret` / `password` / `credential` / `passphrase` / `key` / `cert`
- **D2**: フィールドの型が `Throwable` に代入可能

- **明示リスト**: 上記に当たらないが、**明示的に秘匿と宣言された**フィールド

D1 に**型の制限を課さない**。制限の代わりに §7.3 の性質を使う。

**明示リストは exemption(§7.3.1)の対称形である。** 名前パターンが取りこぼす秘匿値のうち
**既知のもの**をここで宣言する。リストは A5 の pin に含まれるので、追加・削除は目に見える承認行為になる。

| フィールド | 理由 |
|---|---|
| `…HttpAgentOptions.ca: String?` | CA 証明書のパスまたは内容。名前 `ca` は D1 のどの語にも一致せず型も `Throwable` ではないが、§15 の秘匿対象である |

**明示リストが無いと、宣言と検出が食い違う。** §9.1 は `ca` を伏せると定め §22.2 は null ケースを
要求しているのに、検出写像に入らなければ A1 の比較組に入らず、`ca` を `Base64` で出す変異は
A2 しか落とさない。**「秘匿である」と書いた場所と、それを検査する場所を一致させる。**

**L-1 は明示リストで消えない。** ここで宣言できるのは**既知の**取りこぼしだけであり、
`WebviewEditorKey.queryParams` のように**気づかれていない**ものは依然として検出されない。

**判定の入力はこの 3 つだけである(D1 / D2 / 明示リスト)。保持関係を辿る推移閉包は置かない**(理由と残る穴は §7.6)。

### §7.3 sentinel の合成戦略と、非秘匿の明示的宣言

**秘匿フィールドは必ず検査される。検査できない型は失敗させる。**

検査は**出力不変性**で行う。すなわち、**秘匿フィールドだけが異なる 2 つのインスタンスを組み立て、
`toString()` の出力が完全に一致すること**を要求する。

| フィールド型 | 植える 2 値 |
|---|---|
| `String` / `CharSequence` | **1 文字も共有せず、長さも異なる** 2 つの sentinel 文字列 |
| `Throwable` に代入可能 | **同一クラス**のまま、message・`cause`・stack trace・`suppressed` の **4 成分をすべて**独立に変えた 2 つの `RuntimeException` |
| 整数型 / 浮動小数点型 | 十進表記も 16 進表記も共有しない 2 つの値 |
| `Instant` | 異なる 2 つの時刻 |
| `ByteArray` | **1 バイトも共有せず、長さも異なる** 2 つの配列 |
| 上記に当てはまらない型 | **合成戦略なし → 失敗**(A6) |

**「出力に sentinel が現れないこと」では足りない。それは表現に依存した条件である。**
`toString()` が `Base64.getEncoder().encodeToString(privateKey)` を返す、数値を 16 進で出す、
`Instant.toEpochMilli()` を出す — いずれも、探す形を固定した検査を迂回しながら**可逆な秘密を漏らす**。
出力不変性はこれらをすべて捕まえる。値が出力に影響しないなら、どう符号化しても出力は変わらない。

補足:

- **2 値が 1 文字も共有しない**必要があるのは、`toString()` が秘匿値の一部だけを出す場合
  (先頭 4 文字など)に、共有部分が偶然一致して不変性が成立するのを防ぐため。
- **長さも異ならせる**必要があるのは、`token.length` のような**値そのものではない投影**を
  出力する実装を捕まえるため。文字を共有しなくても長さが同じなら不変性が成立してしまう。
  同じ理由で `ByteArray` の 2 値も長さを変える。
- **`Throwable` の 2 値を同一クラスにする**のは、§9.2 が**型は出力してよい**と定めているため。
  クラスが異なると `type=` が変わり、正しい実装が不変性を破ってしまう。
- **クラス以外はすべて変える。** message だけを変えると `cause` / `suppressed` / stack trace が
  両標本で同じになり得るため、`cause.stackTrace` や `cause.cause?.message` を出力する実装でも
  不変性が成立してしまう。**§15 が出力を許すのは型名だけ**なので、型以外の投影はすべて
  不変性で禁じられていなければならない。stack trace は生成位置に依存させず
  `setStackTrace` で異なる合成フレームを与える(headless でも決定的にするため)。
- **配列型の秘匿フィールドを同一性ベースで出力する実装は、不変性を破って失敗する。**
  `ByteArray` をそのまま補間すると 2 インスタンスで `[B@…` が異なるためである。
  これは意図した挙動として受け入れる — 配列の同一性は診断上の価値を持たない。
- 探す形を固定した検査(sentinel の文字列検索)は**廃止しない**。不変性が破れたときに
  「どの sentinel がどう現れたか」を失敗メッセージに載せるための**診断**として併用する。
  受け入れ条件は不変性の側である(A1)。

#### §7.3.1 非秘匿の明示的宣言(exemption)

名前パターンに当たったが**実際には秘匿ではない**フィールドは、**理由を書いた明示的なリストに
載せることでのみ**検査を免れる。リストは A5 の pin に含まれる(= 追加は目に見える承認行為になる)。

| フィールド | 理由 |
|---|---|
| `GitLabAuthorizationToken.tokenExpirationTimestamp: Instant` | 有効期限であってトークンではない。`OAuthTokenProvider.kt:52,74,84` が既に意図的にログ出力しており、`toString()` から外すと診断情報が減る(R5) |
| `…CodeCompletion.enableSecretRedaction: Boolean` | LS の機能フラグ。`Boolean` は 2 値しか取れず秘匿値を運べない |
| `…GitLabLanguageServerConfigurationParams.ignoreCertificateErrors: Boolean` | 設定フラグ。同上 |
| `EgressConfigSnapshot.ignoreCertificateErrors: Boolean` | 設定フラグ。同上 |

**exemption は「検査できない」ではなく「秘匿ではない」を宣言する。** 両者を混同しない。
検査できない(合成戦略が無い)場合の既定は失敗であって exemption ではない。

#### §7.3.2 sentinel を植える範囲

**sentinel は秘匿フィールドにのみ植える。** クラス単位で全 `String` フィールドに植えると、
`ConnectionSnapshot.instanceUrl` / `authFingerprint` のような正当に出力されるべき
フィールドまで「出てはいけない」ことになる。

### §7.4 インスタンスの組み立て

`kotlin-reflect`(`build.gradle.kts:137` で導入済み)の `KFunction.callBy` を用いる。

**デフォルト値に委ねてよいのは非秘匿の引数だけである。
秘匿引数には、デフォルト値の有無にかかわらず必ず明示的に sentinel を渡す。**

この区別は本設計で最も間違えやすい点である。実際
`GitLabLanguageServerConfigurationParams.token` / `HttpAgentOptions.cert` / `.certKey` は
**3 つとも `= null` のデフォルトを持つ**。デフォルトに委ねると、規約テストが組み立てる
インスタンスではこれらが null のままになり、**A1 が最も重要な 3 フィールドについて空虚になる。**

| 引数 | 値 |
|---|---|
| 秘匿フィールド | §7.3 の sentinel。**デフォルトの有無にかかわらず明示的に渡す** |
| 型が **§7.5 の再帰対象**(非 exemption の秘匿フィールドを持つ被検出クラス)であるフィールド(nullable 含む) | §7.5 により、その sentinel を植えた実インスタンスを再帰的に組み立てて渡す。**exemption だけを持つ被検出クラス(`CodeCompletion`)は対象外**で、下の一般規則に従う |
| 上記以外で、デフォルト値を持つもの | 写像に載せない(コンパイラのデフォルトに委ねる) |
| 上記以外の nullable | `null` |
| 上記以外の非 null `String` | 中立文字列(どの sentinel とも一致しない固定値) |
| 上記以外の数値型 | `0` |
| 上記以外の `Boolean` | `false` |
| 上記以外の `List` / `Set` / `Map` | 空 |
| 上記以外の enum | 先頭の定数 |
| 上記に当てはまらない非 null 参照型 | **合成不能 → 失敗**(A6) |

デフォルトに委ねる規則が残る理由は `GitLabAuthorizationToken.tokenExpirationTimestamp`
(`createdAt` と `expiresIn` から計算する式デフォルト)であり、テスト側が `Instant` の値を
発明せずに済む。これは §7.3.1 で非秘匿を宣言済みのフィールドである。

**組み立て後、リフレクションで各秘匿フィールドが実際に sentinel を保持していることを確認する。**
出力不変性は **2 つのインスタンスが実際に異なる秘匿値を持っていて初めて意味を持つ。**
sentinel が注入されなければ 2 つのインスタンスは同一になり、不変性は自明に成立してしまう。
この肯定的な読み戻しが無いと、上記のデフォルト委譲の誤りも §7.5 の再帰の欠落も検出できない。

### §7.5 合成(入れ子)の扱い

**入れ子を再帰的に組み立て、外側の出力を入れ子の sentinel に対しても検査する。**

**再帰元となるのは、非 exemption の秘匿フィールドを 1 つ以上持つ被検出クラスだけである。**
その型のフィールドには、null や中立値ではなく、**そのクラスの sentinel を植えた実インスタンス**を
渡す(nullable であっても渡す)。

**exemption だけを持つ被検出クラスは再帰元にしない。** sentinel を 1 つも運ばないため、
再帰しても検査するものが無い。具体的には `GitLabLanguageServerConfigurationParams.codeCompletion`
は**対象外**である。

対象は今日 2 箇所ある。

| 外側 | フィールド | 入れ子 |
|---|---|---|
| `GitLabLanguageServerConfigurationParams` | `httpAgentOptions: HttpAgentOptions? = null` | `HttpAgentOptions` |
| `EgressConfigSnapshot` | `proxy: ProxyConfig?` | `ProxyConfig` |

**この節が要求する検査は A1 の後段が受け持つ**(外側について「入れ子の秘匿フィールドだけが異なる」
組の出力不変性)。`httpAgentOptions` / `proxy` 自身は D1/D2 の秘匿フィールドではないため、
A1 の前段(自分の秘匿フィールドだけが異なる組)には現れない。

循環参照が生じた場合は失敗させる(A6)。今日の被検出クラスに循環は無い。

**この再帰が覆うのは「既に検出されている外側」だけである。** 保持しているという理由だけで
外側が検出されることはない(§7.2 は推移閉包を置かない)。その帰結は §7.6。

> **なぜ再帰が要るか。** 「入れ子自身が単独で安全なら外側も安全」という含意は、
> **生成 `toString()` が入れ子の `toString()` に委譲する場合にしか成立しない。**
> 本設計は手書きの `toString()` を 12 個持ち込むものであり、外側の上書きが
> `httpAgentOptions?.certKey` のように**入れ子の安全な `toString()` を迂回して直接補間する**ことを
> 何も妨げない。合成の安全性は**論証せず検査する。**

### §7.6 保証範囲 — 完全性を追わない

**この機構が保証するのは「秘匿値を直接保持するクラスの秘匿」である。**
他のオブジェクト経由でのみ秘匿値に到達するクラスは、**別の理由で検出される場合に限り**覆われる。

具体的に開いたままの形はこうである。`data class Envelope(val options: HttpAgentOptions)` や
`data class Envelope(val options: List<HttpAgentOptions>)` は、直接のフィールド名も型も
D1/D2 に当たらないため検出されない。その `toString()` が `options.certKey` や
`options.first().certKey` を**手書きで**補間すれば、`HttpAgentOptions` 自身の安全な `toString()` は
迂回される。

**この穴を塞ごうとすると、任意の型グラフ上で秘匿値への到達可能性を静的に解析することになり、
自然な停止点が無い。** 直接の保持を閉じれば次はコンテナの型引数、次は型引数の型引数、
次は配列、`Map` の値型、と際限がない。

**しかし残余リスクの正体は 1 つに畳める。** 迂回が成立するには、誰かが**手書きの `toString()` で
入れ子の秘匿成分に手を伸ばす**必要がある。**生成 `toString()` は決してそれをしない**
(入れ子の `toString()` に委譲するだけである)。したがって残るのは
「**手書きの `toString()` が漏らす**」という形であり、**これは L-2 として既に受容している制限と
同一のクラス**である。→ **L-5** として明示的に受容する。

**設計判断の根拠**: 本設計の目的は「latent な秘匿漏洩を機構で閉じる」ことであって、
「あらゆる将来のコードに対する完全性」ではない。完全性を追うと、**object レベルの成果物
(12 クラスの `toString()` 上書き)が一切変わらないまま、検証機構だけが際限なく育つ。**

## §8 検出器の不変条件(偽合格の遮断)

前フェーズ(PR #55)で実地に踏んだ検証ツールの偽合格機構 5 件は、すべて
「**信号の不在から『何も捕まえなかった』を推論する**」という同一の形をしていた。
本検出器は同じ形の穴を作りやすい構造なので、「違反ゼロ」に化ける経路を明示的に塞ぐ。

条件そのものは §22 に置く。ここには**各条件が塞いでいる偽合格の機序**を記す。

| 条件 | 塞ぐ偽合格の機序 |
|---|---|
| A3 | コード出力ディレクトリの解決が壊れると、走査は 0 クラスを見て「違反なし」と報告する |
| A4 | `Class.getDeclaredFields()` は `LinkageError` を投げ得る。捕まえて読み飛ばすと、その中に秘匿クラスがあっても静かに通る |
| A5 | 検出器の対象集合が静かに縮む |
| A6 | 「作れなかったから検査していない」が緑になる |

**A5 の期待リストは検出器の出力から作らない。** §6 の 15 個の FQCN と契機フィールド名、
§7.2 の明示リスト、および §7.3.1 の exemption リストをテストコードに直接書く。前フェーズで 2 度確認された一般則
「**テスト対象そのものから期待値を組み立てると、最も起きやすい変異を素通しする**」への対処である。

A5 を**両方向**にする理由: 増えた側が R2(42 件目を止める)の本体、減った側が R3(検出器が壊れた)を捕まえる。

sentinel は**フィールドごとに一意**にする。どのフィールドが漏れたかが失敗メッセージから直接わかるため。

### §8.1 A5 の弱点(実測)

**A5 は production クラスを標本にしているため、検出パターンの語の削除に対して鈍い。** 実測:
被検出 `data class` の中で `key` に一致するフィールドは `HttpAgentOptions.certKey` と
`EgressConfigSnapshot.clientCertificateKeyPath` の 2 つだけで、**どちらも同時に `cert` にも一致する**
(他の `key` 一致フィールドはすべて非 `data class` にあり §7.1 で除外される)。
したがって **D1 から `key` を落としても検出集合は変わらず、A5 は緑のまま通る。**

**これは受容する**(L-7)。パターンの各語を個別に固定するには専用 fixture が要り、
それは §8.4 で放棄した層に属する。パターンの変更は差分レビューで捕まえる。

### §8.2 検査不能クラスが非空だった場合

**非空の検査不能集合を pin して合格させることは、R2/R3 に反する。**
pin されたクラスに後から秘匿フィールドが追加されても、同じ FQCN が引き続き `LinkageError` になる限り
A4 は一致し続け、フィールドを読めないので A5 にも A1 にも現れない。
**正しく実装された検出器のまま、既知の検査不能領域だけが恒久的な盲点になる。**

したがって **A4 は「空であること」を要求する。** U1 が非空だった場合の選択肢は次の 3 つで、
いずれも**ユーザーの判断を要する。実装エージェントの裁量で pin してはならない。**

1. 依存関係を解消して集合を空にする(`build.gradle.kts` の変更は共通制約により禁止のため、
   変更なしで解消できる場合に限る)。
2. bytecode / Kotlin metadata からフィールドと生成 `toString()` の有無を読む代替経路を定義する。
3. 検出範囲を明示的に縮小し、縮小した領域を受容済み制限として記録する。

### §8.3 コメントの欠陥クラスへの注意

本プロジェクトで最頻の欠陥は「**コードが果たさない約束をするコメント**」であり、
一般形は「ある真の理由を『その』理由として述べる」である。本設計の実装では、
**閉じたリストや未検証の網羅性主張をコメントに書かない。**

### §8.4 ハーネス自身はテストで固定しない(信頼境界)

**信頼境界を「テストコード全体」に引く。** 規約テストのハーネス(走査・検出判定・合成・
読み戻し・不変性比較)は**テストコードであり、その正しさは差分レビューが担保する。**

**この層を持たない判断の根拠**:

- 本設計の object レベルの成果物は **12 クラスの `toString()` 上書き**であり、#54 の実害は
  **latent**(補間箇所ゼロ・§4.2)である。
- ハーネスをテストで固定する層を作ると、**その層自身を固定する層**が必要になり、
  fixture を足すたびに問いが 1 段深くなる。設計レビュー #58 では実際にこれが 14 ラウンド続き、
  その間 object レベルの成果物は一度も変わらなかった。
- テストコードの正しさを差分レビューに委ねるのは、多くのプロジェクトが実際に採っている境界であり、
  §7.6 で到達可能性の完全性を降りたのと**同じ判断**を検証の深さについて行うものである。

**帰結**: ハーネスのロジックが静かに壊れた場合(検出パターンの語が消える、
sentinel が注入されない、比較が定数を返す 等)、**テストはそれを捕まえない。**
→ **L-7** として明示的に受容する。

**代わりに設計側で risk を下げる**:

- 判定は名前付き関数が値として返し、テストはその戻り値を assert する
  (`verdict shouldBe Ok` の形。matcher の引数の中で判定を組み立てない)。
  **差分レビューで判定ロジックを読める形にするため**である。
- §11 の処理フローを実装の唯一の情報源とし、各ステップに対応する条件を明記する。

## §9 修正の形

### §9.1 D1 系(6 件)

秘匿成分を伏せ、診断に有用な非秘匿成分を残す。既存の `ProxyConfig.kt:14-16` の形
(`username=${username?.let { "***" }}`)に合わせる。

R5 により残す非秘匿成分の例: `instanceUrl` / `authFingerprint` / `configGeneration` /
`baseUrl` / `logLevel`。

**nullable な秘匿成分に `!!` を使わない。** `token!!` / `certKey!!` は、規約テストが常に非 null の
sentinel を注入する(§7.4)ため A1 では一度も通らない経路であり、**実利用の null で NPE を投げて
本来の障害を覆い隠す**(§13.1)。A2(b) がこの経路を固定する。

**秘匿成分の出力を、その秘匿成分自身の値で条件づけてはならない。**
`if (token.startsWith("glpat-")) token else "***"` のような分岐を書かない。
A1 は**固定した 2 値しか比較しない**ため、テスト標本で偽になる条件に隠れた漏洩は
A1 も有限個の A2 標本もすべて通り抜ける(L-8)。

**秘匿成分の出力を、他のフィールドの値に条件づけてはならない。**
`if (enabled) token else "***"` のような出し分けを書かない。無条件に伏せる。
理由は A1 が非秘匿フィールドを §7.4 の中立状態に固定した組で検査するためで、
条件づけると**規約テストが通る状態と実利用の状態が食い違う**(L-6)。

**上書きは「生成形の再現」を目指さない。** 伏せる成分と、診断に有用な成分を明示的に選ぶ。
`GitLabLanguageServerConfigurationParams` は成分を 12 個持ち、生成形をすべて手書きで再現すると
**成分が 1 つ増えたときに `toString()` だけが黙って古いままになる**。これは §8.3 の欠陥クラスの
`toString()` 版である。成分を明示的に選んだ形は、その約束を最初からしない。帰結は L-4。

`HttpAgentOptions` は `ca` も伏せる。`ca` は名前パターンに掛からないが CA 証明書のパスまたは内容であり、
§15 の秘匿対象である。**パターンは検出器であって、修正の範囲を決めるものではない。**
(検出側は §7.2 の明示リストで揃えてある。)

**§7.5 の再帰対象**(= **非 exemption の秘匿フィールドを持つ被検出クラス**)**を保持するフィールドは、
入れ子の `toString()` に委譲して出力する。**
対象は §7.5 の表と同じ 2 フィールドだけである — `Params` は `httpAgentOptions=$httpAgentOptions`、
`EgressConfigSnapshot` は `proxy=$proxy` の形で出す。
**入れ子の中身に直接手を伸ばさない**(`httpAgentOptions?.certKey` のような補間を書かない)。

**`Params.codeCompletion` は対象外である。** `CodeCompletion` は exemption だけを持つため
§7.5 の再帰対象ではなく、A1 後段も存在しない。委譲を課す理由(下記 2)が当てはまらないので、
出力するかどうかは §9.1 冒頭の一般規則(診断に有用な成分を明示的に選ぶ)に従う。
**この限定が無いと、L-4 で避けたはずの「生成形の再現」を実装者に強いることになる。**

理由は 2 つある。

1. **診断上の価値がある** — mTLS やプロキシが構成されているかは障害調査で要る情報であり、
   入れ子側が自前で伏せているので委譲は安全である(R5)。
2. **委譲しないと §7.5 の再帰と A1 後段が空回りする。** 外側が入れ子を出力しなければ、
   入れ子の値を変えても外側の 2 出力は同じままで、A1 後段はどんな実装でも通ってしまう。
   **委譲を必須にすることで、A1 後段が実際に何かを固定する。**

### §9.2 D2 系(6 件)

`Failed(type=java.io.IOException)` の形。既存の `WebviewUriResolver.kt:35` に一致させる。

**message を落とし、型を残す。** message を落とすのは、`Throwable.toString()` が
クラス名**と** message を出し、message に URI・ファイルパスが入るため。
型を残すのは R5(型を落とすと障害調査が成立しない)。

`cause` が null を取り得るクラス(`PushOutcome.Failed` / `CheckoutResult.Failed`)は
`type=null` を出す(`WebviewUriResolver` の既存形と同じ)。

## §10 システム構成とコンポーネントの責務

**production 側は各 `data class` の `toString()` 上書きのみで、新しい型・層・サービスを
一切導入しない。** 機構はすべてテスト側にあり、production の振る舞いには現れない。

| コンポーネント | 責務 | 依存 |
|---|---|---|
| 各 `data class` の `toString()` 上書き | 自クラスの文字列形から秘匿成分を除く | なし |
| 規約テスト(`SecretRedactionConventionTest`) | リポジトリ全体に対して R1・R2・R3 を固定する | `kotlin-reflect`、コンパイル出力ディレクトリ |
| クラス単位テスト 12 本 | 各 `toString()` の**出力形**を固定する(R4・R5) | なし |

**規約テスト 1 本では足りない。** 規約テストの assert は出力不変性(§7.3)であり、
`toString()` が空文字列を返す変異はこれを通る(空文字列は不変である)。「簡潔にしよう」は
現実に起きる編集で、前フェーズでも文言を短くする方向の変異が受け入れ条件を片方向で素通しした実例がある。

- 規約テスト = 性質をリポジトリ全体に対して固定する(R2 を担うのはこれ)
- クラス単位テスト = 各 `toString()` が**何と言うか**を固定する(R4 を担うのはこれ)

## §11 処理フロー(規約テスト)

**本節は実装の唯一の情報源である**(§8.4)。

```
 1. ConnectionSnapshot::class.java.protectionDomain.codeSource.location
    → プラグイン本体のコンパイル出力ディレクトリ
    ※ パスをハードコードしない(Gradle のレイアウト変更に影響されない)
 2. ディレクトリを再帰走査し .class を列挙
 3. Class.forName(name, initialize = false, loader) で読む
    ※ 初期化しない = Eclipse 依存の静的初期化子を headless で走らせない
    ※ LinkageError は捕まえて「検査不能」集合に記録
 4. KClass.isData == true でないものを除外(§7.1)
 5. getDeclaredFields() を §7.2 の D1 / D2 で判定 → 秘匿フィールドの写像を得る
    ※ §7.2 の明示リストに載るフィールドは秘匿に加える
    ※ §7.3.1 の exemption リストに載るフィールドは秘匿から外す
 6. 走査総数 > 0 を確認(A3)/ 検査不能集合が空であることを確認(A4)/
    秘匿クラス集合 + exemption リストを手書き期待リストと双方向照合(A5)
 7. 秘匿フィールドを持つ各クラスについて §7.4 で組み立て
    ※ 秘匿引数はデフォルトに委ねず必ず sentinel を渡す
    ※ 型が §7.5 の再帰対象(非 exemption の秘匿フィールドを持つ被検出クラス)の
      フィールドは再帰的に組み立てて渡す。exemption だけの `CodeCompletion` は対象外
    ※ 合成戦略が無い / 組み立て不能 / 循環 / toString() が throw は fail(A6)
 8. 組み立て結果をリフレクションで読み戻し、各秘匿フィールドが
    実際に sentinel を保持していることを確認(§7.4 末尾)
 9. 秘匿フィールドだけが異なる 2 つ目のインスタンスを同様に組み立て、
    両者の toString() 出力が完全に一致することを assert(A1 前段)
    ※ 不一致のとき、どの sentinel がどう現れたかを失敗メッセージに載せる(§7.3 の診断)
10. §7.5 の対象クラスについては、さらに「入れ子インスタンスの秘匿フィールドだけが異なる」
    外側の組を、入れ子の秘匿フィールドごとに列挙して組み立て、
    各組の出力が一致することを assert(A1 後段)
    ※ 外側自身の秘匿フィールドは両者で同一に保つ。変えるのは入れ子の中の 1 フィールドだけ
```

## §13.1 エラー処理

### production 側

**`toString()` は例外を投げてはならない。** `toString()` はログ出力・デバッガ・例外メッセージから
呼ばれるため、ここで throw すると**本来のエラーを覆い隠す**。

具体的な危険は nullable 成分にある。`PushOutcome.Failed` / `CheckoutResult.Failed` /
`WebviewResolution.Failed` は `cause: Throwable?` を持つので、`cause.javaClass.name` と書くと
`cause` が null のとき NPE になる。`cause?.javaClass?.name` を使う(既存の
`WebviewUriResolver.kt:35` がこの形)。§9.2 が `type=null` の出力を規定しているのはこのため。

### テスト側

規約テストが遭遇し得るエラーは 5 種。**いずれもスキップせず失敗として報告する。**

| エラー | 扱い |
|---|---|
| クラス読み込み時の `LinkageError` | 「検査不能」集合に記録し、**空であること**を確認(A4) |
| 組み立て失敗(合成不能な型・`callBy` の失敗) | 失敗(A6)。FQCN と解決できなかった引数の型を報告する |
| 秘匿フィールドの型に §7.3 の合成戦略が無い | 失敗(A6)。FQCN・フィールド名・型を報告する |
| 入れ子(§7.5)の循環参照 | 失敗(A6)。循環の経路を報告する |
| `toString()` 呼び出し自体が throw | 失敗(A6)。FQCN と例外の型を報告する |

**いずれも「検査できなかった」を「違反がなかった」と読ませない**ことが要件である(R3)。

## §14 既存機能への影響

### §14.1 シリアライズへの影響 — なし

Gson はフィールドのリフレクションで JSON を構築するため、`toString()` の上書きは
シリアライズ結果に影響しない。したがって以下は**バイト単位で不変**である。

- `OAuthSecretStorage.kt:32` の `gson.toJson(token)`(SecretStorage の永続形式)
- lsp4j 経由で LS に送る `GitLabLanguageServerConfigurationParams` のワイヤ形式

これは §16.2 のラッパー型案(フィールドの**型**を変える案)とは異なる。
型を変えれば両方が壊れるが、`toString()` の上書きでは壊れない。

### §14.2 既存テストへの影響

対象 12 クラスの `toString()` 出力に依存している既存テストは掃いた範囲で存在しない。

`LanguageServerProxyManagerProxyConfigTest.kt:30`(`config.toString().contains("s3cret") shouldBe false`)は
`ProxyConfig` について規約テストと性質が重複するが、**残す**。
このテストは「プロキシ設定の解決」という別の production 経路の中で見ているものであり、
削るとその経路側の被覆が減る。

### §14.3 受容済みの制限

| ID | 制限 | 根拠 |
|---|---|---|

| L-3 | `toString()` 以外の経路(独自のフォーマッタ、`Gson().toJson()` をログに出す等)は対象外 | 本設計は生成 `toString()` の欠陥クラスに限定している |

## §15 秘匿・ログ・監査

本設計は**秘匿の機構そのもの**であるため、設計の適用対象が本設計の産物と重なる。

- 規約テストの失敗メッセージには sentinel(テストが生成した固定文字列)と FQCN・フィールド名のみが載る。
  実際の資格情報は**テスト実行時に存在しない**(すべて合成値)。
- 修正後の `toString()` が出力してよいものは、非秘匿成分と例外の**型名**のみ(§9)。

**前フェーズからの申し送り**: PR #55 の秘匿テストは `shouldNotContain "/"` という **proxy** で
担保されており、区切り文字を含まない漏洩(裸のファイル名・トークン)を捕まえない。
本設計の規約テストは**出力不変性**で担保するため表現方法に依存せず、
裸のファイル名も `Base64` 等で符号化された値も捕まえる。

## §16 検討したが採らなかった案

### §16.1 ソース走査による lint テスト

`src/main/kotlin` をテキストで走査し、`data class` の主コンストラクタに秘匿名/`Throwable` があれば
`override fun toString(` の存在を要求する案。

**却下理由 3 点**:

1. **`override fun toString()` の存在は性質ではなく性質の proxy。** 上書きは存在するが依然として
   トークンを出す実装で緑になる。
2. **Kotlin の主コンストラクタをテキストで切り出すのは見た目より脆い。**
   実証: `HttpAgentOptions` は 1 行で書かれているため、行頭 `val` を見る走査から漏れた(§6 の注記)。
   `GitLabLanguageServerConfigurationParams` は入れ子 `data class` を 8 個持つ。
3. 入れ子の漏洩(§4.3 の 2)を構造上検出できない。

### §16.2 ラッパー型(`SecretString` 等)への移行

秘匿成分の**型**を、`toString()` が固定文字列を返すラッパー型に置き換える案。

**却下理由 3 点**:

1. `GitLabAuthorizationToken` は SecretStorage の永続 JSON 形、
   `GitLabLanguageServerConfigurationParams` は LS のワイヤ形式であり、
   **両方に Gson の `TypeAdapter` が要る**。後者は lsp4j 側の Gson 構成に手を入れる話になる。
2. 共通制約 5「プロトコル定数・LSP/webview メッセージ仕様は実装前に実ソースで確定」に対して、
   ワイヤ形式を変えないという選択のほうが risk が小さい。
3. `Throwable` の message 漏洩(D2・6 件)には何の効果もない。

### §16.3 ハーネス自身をテストで固定する層

検出器の各分岐(パターンの語ごと・失敗分岐ごと・合成戦略の型ごと)に専用 fixture を置き、
分岐を消す変異が対応する 1 本だけを落とすようにする案。

**却下理由**: §8.4。この層を作ると**その層自身を固定する層**が必要になり停止点が無い。
本設計の object レベルの成果物は 12 クラスの `toString()` 上書きであり、実害は latent である。
**規模が目的に見合わない。** 結果として生じる穴は L-7。

### §22.1 受け入れ条件の識別性

各条件は「守れている一例」ではなく性質を検査していなければならない。
以下の変異がそれぞれ対応する条件だけを落とすこと(実装時に変異前後の実出力を提出する)。

**本表は production コードの変異のみを対象とする。** ハーネスの変異は L-7 により差分レビューの責務であり、
変異証跡の対象外である(§8.4)。

| 変異 | 落ちるべき条件 |
|---|---|
| 任意の 1 クラスの `toString()` 上書きを削除 | A1(そのクラス)+ A2(そのクラス) |
| 任意の 1 クラスの `toString()` を `""` にする | A2 のみ(A1 は通る。空文字列は不変) |
| 任意の 1 クラスの `toString()` が秘匿値を `Base64` で符号化して出す | A1 + A2 |
| `toString()` を基準標本の値を埋め込んだ**定数文字列**にする | **クラスの構造ごとに異なる**(下表)。A1 はどの場合も通る — 定数は秘匿値に依存しない |
| nullable な秘匿成分の参照を `!!` にする(`token!!` / `certKey!!`) | **A2(b) のみ**(A1 も A6 も通る。§7.4 は常に非 null を注入するため null 経路を通らない) |
| §9.2 で例外の型を出力から落とす | A2 |
| `cause?.javaClass?.name` を `cause!!.javaClass.name` にする | A2(null ケース)。§13.1 |
| §9.1 に反して秘匿の出力を他フィールドに条件づける | **どの条件も落とさない**(L-6)。差分レビューで捕まえる |
| 新しい秘匿名フィールドを持つ `data class` を追加する — **フィールドの型に §7.3 の合成戦略がある場合**(`String` / `Throwable` / 数値 / `Instant` / `ByteArray`) | A5(期待リストとの不一致)+ A1(生成 `toString()` が値に依存する) |
| 同上 — **フィールドの型に合成戦略が無い場合**(`Boolean` など。D1 は型を制限しないので実在し得る) | A5 + **A6**(インスタンスを合成できないため A1 は発火しない)。開発者は §7.3.1 の exemption に理由付きで載せるか、§7.3 に合成戦略を足すかを選ぶ |
| 既存の被検出クラスから秘匿フィールドを削除する | A5(減った側) |
| `HttpAgentOptions` の `toString()` を削除する | A1 前段(自身)+ A1 後段(`Params` の入れ子組)+ A2。**A1 後段が落ちるのは §9.1 が外側に委譲出力を課しているため** — 外側が入れ子を出力しない実装なら外側の 2 出力は同じままで A1 後段は落ちない |

#### 定数化変異がクラス構造ごとに落とす条件

「任意の 1 クラス」と書くと**クラスごとの構造差を踏み潰す**(round 16・17 の指摘)。
定数化変異について、12 クラスを構造で 5 群に分ける。

| 群 | クラス | 非秘匿成分を残すか | nullable 秘匿成分 | 落ちる条件 |
|---|---|---|---|---|
| (i) | `ConnectionSnapshot` / `GitLabAuthorizationToken` / `ConfigurationValidationRequest` | 残す | 無し | **A2(a) のみ** |
| (ii) | `GitLabLanguageServerConfigurationParams` / `EgressConfigSnapshot` | 残す | 有り | **A2(a) + A2(b)** |
| (iii) | `HttpAgentOptions` | **残さない**(3 成分すべて秘匿) | 有り | **A2(b) のみ**(A2(a) は空) |
| (iv) | `PushOutcome.Failed` / `CheckoutResult.Failed` | 残さない(例外型の投影のみ) | 有り(`cause?`) | **A2(a)(型の投影)+ A2(b)** |
| (v) | `DiscussionsLoader.Failed` / `DiscussionWriteOutcome.Definite` / `.Ambiguous` / `LoadOutcome.Failed` | 残さない(例外型の投影のみ) | 無し(`cause` は非 null) | **A2(a)(型の投影)のみ** |

**(v) は controller の掃引で発見した。** これらは出力が `Failed(type=…)` だけなので、
A2(a) が**例外型の投影**を覆わない限り、基準標本と同じ定数への置換で**どの条件も落ちない**
(A1 は §7.3 により同一クラスの 2 値を使うので型が変化せず、定数と一致してしまう)。
A2(a) を「非秘匿成分**および秘匿値の許された投影**」に広げたのはこのためである。
